# md-reader 文件树文件操作与拖拽重组方案

## 方案概述

### 1. 总体目标和范围

本方案用于为 `md-reader` 左侧文件树补齐一组真正可用的文件管理能力，目标是在保持当前 Markdown 工作区、profile 恢复、文档打开和本地 bridge 架构不被打散的前提下，让用户可以直接在左侧树完成以下操作：

- 在搜索栏右侧创建新文档
- 在搜索栏右侧创建新文件夹
- 在文件树中把文档真实拖入文件夹以重组目录
- 使用自定义右键菜单执行拷贝链接、创建副本、重命名、删除

本轮范围固定为“真实文件系统操作”，不是视觉层假排序：

- 拖拽后的结果必须真实改变磁盘上的路径或目录结构
- 文件树刷新后必须自然反映新路径
- 当前打开文档、顶部标签、活动文档路径和本地会话恢复链路都必须跟随更新

本方案包含：

- 左侧搜索区新增按钮的职责与交互边界
- 文档拖拽重组目录的第一版规则
- 自定义右键菜单的动作定义
- bridge 文件操作 API 的扩展设计
- 前端状态、会话状态和 profile 状态的职责拆分
- 后续实施阶段、验证口径和风险控制

本方案不包含：

- 文件夹自身拖拽
- 跨项目拖拽
- 拖出应用到系统文件管理器
- 多选批量移动 / 批量删除
- 回收站 / 撤销栈 / 历史版本恢复
- 独立“文件属性面板”或面包屑级移动器
- 纯视觉排序层或额外 `fileOrder` 持久化模型

### 2. 各阶段任务概要

阶段一：收敛文件操作协议与安全边界

- 主要工作：补齐 bridge 的新建、复制、重命名、删除、移动 API，并复用现有 `contentRoots` 路径约束，固定错误码和返回结构。
- 预期成果：前端不再假设文件系统写权限，所有文件树操作都通过同一条本地 bridge 能力完成。
- 执行顺序：必须最先完成，因为其他交互都依赖它。

阶段二：接入创建入口与右键菜单

- 主要工作：在搜索栏右侧增加“新建文档/新建文件夹”按钮，自定义右键菜单，补齐文件节点的创建副本、重命名、删除、拷贝链接，以及目录节点的新建子项与拷贝路径。
- 预期成果：用户可在文件树中完成基础文件管理，不必跳出到外部文件管理器。
- 执行顺序：先按钮，再右键菜单。

阶段三：接入真实拖拽移动文档

- 主要工作：为文档行增加 pointer drag 生命周期、drop 命中、移动提交、树刷新与当前会话路径联动。
- 预期成果：文档可以拖入文件夹，并真实重组目录。
- 执行顺序：在文件操作 API 稳定后进行，避免拖拽只做半链路预览。

阶段四：补齐会话联动与回归验证

- 主要工作：处理当前打开文档、顶部标签、活动路径、保存中的草稿、路径冲突和错误提示；补齐组件测试、App 联动测试和 bridge 侧测试。
- 预期成果：文件树管理能力与现有工作区模型协同工作，不破坏打开文档、自动保存和恢复链路。
- 执行顺序：功能接通后统一回归。

### 3. 整体结构框架

本轮建议按六层组织：

- `server/project-*`
  - 承担文件系统级真相：路径校验、创建、复制、移动、重命名、删除
- `server/bridge-server.mjs`
  - 暴露统一 HTTP API，并把错误码、冲突信息和刷新后节点路径返回给前端
- `src/workspace/local-bridge-access.ts`
  - 承担 bridge 客户端封装，不让组件层直接拼接 URL
- `src/App.tsx`
  - 承担文件树刷新、当前活动文档重定向、标签路径同步、本地会话恢复写回
- `src/app/WorkspaceLayout.tsx`
  - 承担搜索栏右侧按钮、右键菜单、文档拖拽 UI 和文件树行级交互
- `src/workspace/file-tree.ts`
  - 继续只负责按路径构造树，不承担拖拽语义或顺序持久化

## 现状证据

### 1. 左侧搜索区和文件树入口都在 `WorkspaceLayout`

当前左侧搜索区和文件树渲染都集中在 [WorkspaceLayout.tsx](/C:/Code/md-reader/src/app/WorkspaceLayout.tsx:653) 附近：

- 搜索框区域当前是一个 `panel__search--with-favorites` 工具条
- 左侧已有收藏过滤按钮
- 文档行和目录行都在 `WorkspaceFileTree` 内渲染
- 文档行右侧操作区当前只承载收藏和隐藏相关动作

这意味着：

1. “新建文档 / 新建文件夹”按钮最自然的落点就是现有搜索区右侧，而不是放入顶栏。
2. 右键菜单和拖拽都应落在文件树行本身，不应引入第二套列表组件。

### 2. 当前文件树没有“位置”概念，只有路径树概念

当前 [file-tree.ts](/C:/Code/md-reader/src/workspace/file-tree.ts:6) 只做两件事：

- 根据路径数组构建目录/文件树
- 在渲染前叠加搜索、隐藏、收藏等过滤

当前节点类型 [file-tree-types.ts](/C:/Code/md-reader/src/workspace/file-tree-types.ts:1) 只有：

- `kind`
- `name`
- `path`
- `children`
- 隐藏状态元数据

并没有：

- 排序索引
- 拖拽句柄
- drop 位置
- 父目录引用
- 移动后的目标语义

这说明本轮若采用“真实路径移动 + 重新扫描构树”，就可以继续复用现有树模型；反过来，如果引入额外视觉排序层，反而会强行扩张树数据模型。

### 3. 当前 bridge 只支持 tree/document/profile/service 能力

前端 bridge 客户端 [local-bridge-access.ts](/C:/Code/md-reader/src/workspace/local-bridge-access.ts:98) 当前只覆盖：

- 项目列表与激活项目
- 文件树路径列表读取
- 文档内容读取与保存
- profile 读取与保存
- bridge 服务控制

后端 [bridge-server.mjs](/C:/Code/md-reader/server/bridge-server.mjs:163) 当前也只有：

- `GET /tree`
- `GET /document`
- `POST /document`
- profile 相关接口

没有：

- create document
- create folder
- duplicate
- rename
- move
- delete

因此你这次要的第 1 项和第 3 项，都不是单纯前端补按钮或菜单能完成的，必须补 bridge API。

### 4. 当前会话真相层在 `App.tsx`

当前 [App.tsx](/C:/Code/md-reader/src/App.tsx:893) 负责：

- 通过 bridge 拉取路径数组并 `buildFileTree(...)`
- 维护 `session.tabs`
- 维护 `activeDocumentPath`
- 在打开文档、切标签、恢复会话时按路径联动

这意味着只要文档路径真实变化，后续必须同步处理：

- 当前活动文档路径
- 已打开标签页中的 `documentPath`
- `openDocumentPaths`
- `tabStateByDocument`
- `readingProgressByDocument`

否则会出现“文件树已经移动，但打开标签还指向旧路径”的断裂状态。

## 需求收敛与关键决策

### 1. 拖拽按“真实移动文件”理解，不做纯视觉排序

用户已经明确确认，拖拽目标是“真实移动文件 / 拖入文件夹重组目录”，因此本轮不引入额外排序层，也不保存“用户自定义列表顺序”。

推荐理由：

1. 当前文件树本质是磁盘路径树，而不是独立数据库列表。
2. 新建、复制、重命名、删除都天然围绕真实路径工作，拖拽若只改显示顺序会与这些动作产生双真相。
3. 重新扫描路径再构树，正好符合当前 `scanMarkdownTree -> buildFileTree` 的实现边界。

### 2. 第一版只允许拖动文档，文件夹只作为放置目标

第一版范围固定为：

- 文档可以拖动
- 文件夹可以接收拖入
- 文件夹不支持被拖动

推荐理由：

1. 目录拖目录会立刻引入祖先/子孙循环校验、整棵目录重命名、副作用放大等问题。
2. 你当前优先想补的是“快速重组文档位置”，不是做完整文件管理器。
3. 先把文档移动链路打通，更容易控制错误恢复和打开文档联动。

### 3. 新建入口固定在搜索栏右侧，不放进顶栏

现有搜索栏已经是文件树局部工具条，因此：

- “新建文档”
- “新建文件夹”

都应放在搜索框右侧，与收藏过滤同属文件树局部操作，而不是全局顶栏操作。

这样可以避免：

- 把局部目录管理误提升为全局工作区模式
- 新建动作失去当前文件树上下文

### 4. 右键菜单只做树节点上下文菜单，不接管整页右键

本轮自定义右键菜单只在文件树节点上生效：

- 文件节点：支持全部动作
- 文件夹节点：第一版只支持“新建子项、拷贝路径”

结合本轮复核后的收敛边界，第一版固定为：

- 文档节点：`拷贝链接 / 创建副本 / 重命名 / 删除`
- 文件夹节点：`新建文档 / 新建文件夹 / 拷贝路径`

这样做的理由是：

1. 目录递归复制、目录重命名和目录删除都会立刻引入子树级路径联动与高风险文件操作。
2. 你当前优先要的是“快速重组文档 + 基础创建入口”，不是完整文件管理器。
3. 将目录动作收敛为“创建子项 + 拷贝路径”后，第一版可以避免把目录级 destructive action 混入上线范围。

### 5. “拷贝链接”按项目内相对路径链接理解

当前产品还没有正式的跨设备分享 URL，因此“拷贝链接”第一版应定义为：

- 拷贝当前项目内相对路径
- 在可能的情况下附带应用可识别的打开语义

推荐落法有两个：

1. 最小方案：只拷贝相对路径，如 `docs/api/reference.md`
2. 增强方案：拷贝可读链接串，如 `md-reader://open?project=<id>&path=<encoded-path>` 或应用内约定格式

第一版推荐先做最小方案，原因是当前仓库里还没有稳定的 deep-link 协议证据。

同时需要明确：这里的“拷贝链接”第一版其实是**拷贝项目内路径引用**，不是跨设备可点击分享链接。实现和文案都不应暗示它已经具备正式 deep-link 能力。

## 交互方案

### 1. 搜索栏右侧按钮

建议将左侧搜索区扩展为三段：

- 左：现有收藏过滤按钮
- 中：搜索输入框
- 右：`新建文档`、`新建文件夹`

按钮行为建议：

默认落点优先级建议固定为：

1. 若当前是从目录节点菜单触发，则在该目录下创建
2. 若当前文件树存在显式选中目录上下文，则在该目录下创建
3. 若当前存在活动文档，则在该文档所在目录创建
4. 若以上都没有，则在当前项目根内容目录创建

第一版不要弹复杂对话框，推荐采用轻量命名流：

1. 点“新建文档”后，先创建临时命名输入态，默认建议名 `未命名文档.md`
2. 点“新建文件夹”后，默认建议名 `未命名文件夹`
3. 若目标路径冲突，由 bridge 返回结构化错误，前端提示用户改名

### 2. 文档拖拽规则

第一版拖拽规则固定为：

1. 只能从文档行主体开始拖动
2. 拖到文件夹行上方时，文件夹高亮为“放入该目录”
3. 不支持拖到文档前后做“插入排序”
4. 放开后立即调用 bridge 移动文件
5. bridge 成功后重新扫描树并刷新当前工作区路径状态

这里需要明确写死：**第一版拖拽只解决“改变父目录”**，不解决“同目录内人工排序”。

原因是：

1. 当前树没有显式顺序元数据，只有真实路径树。
2. 同目录内“前后插入”会被用户自然理解为排序能力，但当前数据模型并不支持这层真相。
3. 如果保留“可拖到文档前后”的表述，后续实现要么做出误导性的假交互，要么被迫引入额外排序层，都会偏离本轮范围。

### 3. 自定义右键菜单

建议文件节点菜单顺序如下：

1. `拷贝链接`
2. `创建副本`
3. `重命名`
4. `删除`

建议目录节点菜单顺序如下：

1. `新建文档`
2. `新建文件夹`
3. `拷贝路径`

交互约束：

- 右键菜单打开时不触发文档打开
- 点击菜单外部、按 `Escape`、切换窗口时关闭菜单
- 菜单项执行后立即关闭菜单
- 危险动作 `删除` 必须有确认层，至少是浏览器 confirm 级别；更推荐项目内轻量确认 popover

### 4. 重命名与删除

重命名建议第一版使用行内输入态，不开全页弹窗。

删除建议规则：

- 删除文档：直接删除文件
- 目录节点：第一版不提供删除动作

这里推荐第一版不开放目录级删除，理由是：

1. 当前产品没有回收站或撤销
2. 一旦误删整目录，风险远高于误删单文档
3. 目录删除即便限制为空目录，也会诱导用户期待目录级 rename/delete 是完整支持的，而本轮不准备承接子树级路径联动和风险控制

### 5. 创建副本

文档副本建议按常见规则生成：

- `foo.md` -> `foo copy.md`
- 若冲突则 `foo copy 2.md`

副本创建后建议：

- 刷新树
- 自动打开新副本文档
- 将其设为当前活动文档

这样符合“复制后继续编辑副本”的常见心智。

## 数据与接口设计

### 1. 前端不新增独立文件顺序状态

当前 `fileTree` 仍以桥接返回路径数组重建，不新增：

- `fileOrder`
- `manualSort`
- `dropIndexPersistence`

本轮新增的前端状态应只限于临时交互态，例如：

- 当前右键菜单目标节点
- 当前重命名输入态
- 当前拖拽中的文档路径
- 当前 drop 目标类型与高亮位置
- 当前异步文件操作 pending 状态

### 2. bridge API 扩展建议

建议在 `server/bridge-server.mjs` 增加独立文件操作路由，例如：

```txt
POST   /api/projects/:projectId/nodes/create-document
POST   /api/projects/:projectId/nodes/create-directory
POST   /api/projects/:projectId/nodes/duplicate
POST   /api/projects/:projectId/nodes/rename
POST   /api/projects/:projectId/nodes/move
POST   /api/projects/:projectId/nodes/delete
```

推荐不要把所有动作都塞进一个 `POST /nodes/action`，原因是：

- 每个动作的输入约束不同
- 错误码和返回结构更容易清晰化
- 前后端测试更容易分组

### 3. 路径安全边界

当前 [project-reader.mjs](/C:/Code/md-reader/server/project-reader.mjs:18) 已经具备：

- 相对路径归一化
- 禁止绝对路径
- 禁止 `..` 穿越
- 限制在 `contentRoots` 内

这套边界应继续复用到：

- 新建路径
- 重命名目标路径
- 移动目标路径
- 删除路径

不要为文件操作单独写一套更宽松的路径解析逻辑。

### 4. 返回结构建议

为减少前端二次猜测，bridge 文件操作成功后建议统一返回：

```ts
{
  ok: true
  path: string
  nextPath?: string
  kind: 'file' | 'directory'
  treePaths: string[]
}
```

其中：

- `path` 表示原路径或新建后路径
- `nextPath` 用于 rename/move 这类“旧路径 -> 新路径”动作
- `treePaths` 直接返回刷新后的路径数组，避免前端再单独补一次 tree 请求

第一版这样做的好处是：

1. 操作成功后可直接 `setFileTree(buildFileTree(treePaths))`
2. `App.tsx` 能同步修正当前文档和 tabs 路径
3. 减少“操作成功但树刷新慢一步”的闪烁

这里建议将“成功后直接返回完整 `treePaths`”标注为**推荐方案**，不是唯一实现约束。若实现阶段评估全量扫描成本或 bridge 复杂度不合适，也允许退回“操作成功后前端主动再拉一次 `/tree`”。

### 5. 错误码建议

建议 bridge 至少暴露这些结构化错误：

- `PATH_ALREADY_EXISTS`
- `PATH_NOT_FOUND`
- `TARGET_NOT_DIRECTORY`
- `DIRECTORY_NOT_EMPTY`
- `INVALID_TARGET_PATH`
- `ACTIVE_DOCUMENT_DIRTY_NEEDS_CONFIRM`

其中最后一个错误码可选。如果实现阶段决定在“未保存草稿被外部路径操作影响”时强制确认，就需要它；如果先按最小实现直接同步路径并保留草稿，则可以暂不引入。

## 工作区联动规则

### 1. 当前活动文档

若当前活动文档被：

- 重命名
- 移动
- 创建副本并切换到副本

则 `activeDocumentPath` 必须同步更新到新路径。

若当前活动文档被删除：

- 应关闭对应标签
- 若还有其他标签，切到最近的替补标签
- 若无其他标签，正文区进入空状态

### 2. 已打开标签页

`session.tabs` 中所有命中的 `documentPath` 都必须同步改写。

同时还要同步改写：

- `openDocumentPaths`
- `tabStateByDocument`
- `readingProgressByDocument`

否则刷新后仍会从旧路径恢复标签，形成悬挂状态。

这里必须区分两类改写：

1. **文件级精确改写**
   - 适用于文档 rename / move
   - 规则是 `oldPath -> newPath`
2. **目录级前缀改写**
   - 适用于目录 rename / move
   - 规则是把所有 `oldDirPrefix/...` 批量改写成 `newDirPrefix/...`

虽然第一版目录节点不开放 rename/delete，但这条规则仍应保留在方案里，原因是：

- bridge 和 `App.tsx` 的路径联动 helper 最好一开始就按“精确改写 + 前缀改写”两类能力设计
- 后续若扩展目录 rename/move，不必回头重做整个路径联动模型

### 3. 草稿与自动保存

最敏感的场景是：

- 文档已打开
- 有未保存草稿
- 用户又对该文档执行重命名、移动或删除

第一版推荐规则：

1. 对“当前正在编辑且草稿未保存”的文档执行重命名或移动时，不允许直接裸操作；必须先冻结 autosave，并优先执行一次 `flushActiveDraft('leave')` 或同等级显式保存流程。
2. 若 flush 成功，再执行 rename / move，并在操作完成后同步把当前 tab 的 `documentPath` 改成新路径，保留草稿内容不丢。
3. 若 flush 失败，则中止本次路径操作，并提示用户先处理保存失败或冲突。
4. 对“当前正在编辑且草稿未保存”的文档执行删除时，必须先确认，再关闭标签并放弃草稿。

这样收敛的理由是：

1. 当前 autosave 和 flush 都直接以路径作为保存目标，若 rename/move 与 pending autosave 交叉，容易继续向旧路径写入。
2. 重命名/移动本质不改内容，flush 成功后再改路径，才能避免旧路径保存竞态。
3. 删除会使草稿失去落点，不能静默处理。

### 4. profile 状态

本轮不建议把任何文件管理动作写入 profile：

- 目录展开状态仍然可以继续写 profile
- 隐藏/收藏仍然归 profile
- 但新建、移动、重命名、删除都属于文件系统真相，不应走 profile 持久化

## 主要风险与应对

### 1. 同级“前后插入”语义与当前树排序模型冲突

当前树天然按路径排序，不存在人工顺序层。

应对：

- 第一版把拖拽价值收敛到“改变父目录”
- 明确不承诺同目录内手工排序

### 2. 路径变化后会话恢复链路残留旧键

当前本地状态里不仅有 `activeDocumentPath`，还有多个以路径为键的 map。

应对：

- 把路径替换逻辑集中到 `App.tsx` 的单点 helper
- helper 至少拆成“文件级精确改写”和“目录级前缀改写”两类
- 每类操作都从同一 helper 走

### 3. rename / move 与 autosave 竞态

当前 autosave 和 flush 都直接按当前路径写 bridge。

应对：

- rename / move 前先冻结 autosave
- 先 flush 成功，再执行路径操作
- flush 失败则中止本次路径操作

### 4. 拖拽和点击/右键容易误触

文件树当前是高频导航区，误触会直接影响可用性。

应对：

- 设定最小拖拽阈值
- 限定只有文档行主体能启动拖拽
- 右键菜单与拖拽状态互斥

### 5. 目录能力未来扩张时可能漏掉子树级路径联动

应对：

- 第一版先把目录动作收敛为“新建子项 + 拷贝路径”
- 但路径联动 helper 设计时预留目录前缀改写能力

## 建议执行顺序

1. 先补 bridge 文件操作 API
2. 再补 App 的路径联动与会话改写
3. 然后接入新建入口和右键菜单
4. 最后接入真实拖拽与回归验证

按这个顺序做，能避免出现“UI 先有了，但落地动作还没有真相层”的半成品状态。

## 实施补记（2026-07-07）

本轮按上述边界落地后，真机排查额外证明了两个关键点：

1. “无法拖入文件夹”不能只按前端事件猜测，必须区分“拖拽事件是否触发”和“真实移动请求是否成功”。
2. 文件树文件操作上线后，`profile` 返回结构也属于路径联动链路的一部分，不能只看 drag/drop 本身。

### 1. 真机根因收敛

真实浏览器排查结果显示：

- 前端 `dragstart -> dragover -> drop` 事件链是正常的
- `POST /api/projects/:projectId/nodes/document/move?profileId=...` 已经被真实发出
- 用户侧“看起来还是不能移动”的第一层根因是本地还在跑旧的 `bridge-server` 进程，导致新路由返回 `404`
- 旧进程清掉并重启后，真实文件已经可以被移动到目标目录
- 随后暴露出的第二层根因是：bridge profile 默认结构缺少 `navigation.hiddenPaths` 和 `navigation.favoritePaths`，前端在路径改写时命中 `undefined.map(...)`，导致移动后 UI 状态链路中断

因此，这个能力的真实闭环不是“把拖拽事件接上就算完成”，而是：

- 事件链能命中目录目标
- move HTTP 路由已在当前 bridge 进程生效
- 文件真实落盘移动成功
- `session` / `localState` / `profile.navigation` 的路径联动都能完成

### 2. 本轮额外收口

基于这次真机排障，实施口径补充为：

- `WorkspaceLayout` 的目录行和目录按钮若同时承接 drag/drop 事件，必须显式阻断冒泡，避免一次 drop 触发两次 move 请求
- `server/project-profiles.mjs` 的默认 profile 和 normalize 流程必须稳定返回：
  - `navigation.hiddenPaths`
  - `navigation.favoritePaths`
- `document-path-mutation` 侧即便面对旧 profile 或缺字段数据，也要做最小兜底，避免一次历史脏数据把整条路径联动打断

### 3. 当前验证口径更新

除原方案中的静态验收项外，建议把真机验证明确拆成三段：

1. **事件层**
   - 文档拖起后，目录目标能进入高亮态
2. **请求层**
   - 真机拖拽后，能看到 `nodes/document/move` 请求返回 `200`
3. **结果层**
   - 磁盘真实路径发生变化
   - 文件树刷新后只保留新路径
   - 当前 tab / `activeDocumentPath` / `openDocumentPaths` / `profile.navigation` 不再引用旧路径

如果只验证第 1 段或只验证 Vitest 组件测试，无法证明“真实拖拽移动文档”已经完成。
