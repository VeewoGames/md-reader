# md-reader 文件树自由排序与持久化方案

## 方案概述

### 1. 总体目标和范围

本方案用于为 `md-reader` 左侧文件树补齐“同级自由排序并固定化”的能力。目标是在不改变当前 Markdown 项目扫描、文件内容读写、profile 切换和本地 bridge 架构边界的前提下，让用户可以直接在文件树中拖拽调整文档与文件夹的显示顺序，并在刷新、重启和切换 profile 后稳定恢复。

本轮已确认的需求边界如下：

- 文件夹和文档在同级内允许完全自由混排
- 排序结果按 `profile` 独立保存，不同 profile 可以拥有不同顺序
- 搜索结果和“只看收藏”这类过滤视图中不允许拖拽排序
- 排序目标是“文件树显示顺序固定化”，不是移动真实磁盘路径

本方案包含：

- 文件树手工排序模型设计
- 文件树构建与排序应用链路
- 同级拖拽交互与禁拖边界
- profile 持久化与排序状态修正策略
- 风险点、验证口径与实施阶段

本方案不包含：

- 真实文件系统目录顺序修改
- 跨项目排序共享
- 多选批量排序
- 搜索结果视图内排序
- 新的独立排序控制器或 grip 把手
- 文件夹拖入自身后代这类真实路径移动问题

### 2. 各阶段任务概要

阶段一：补齐排序模型与纯逻辑 helper

- 主要工作：在 `workspace` 层新增文件树顺序的 normalize、apply、reorder、rename/move/delete 修正逻辑。
- 预期成果：文件树顺序不再依赖扫描返回顺序，而是由一层独立、可持久化的手工顺序模型控制。
- 执行顺序：最先完成，因为 UI 和持久化都依赖它。

阶段二：接入 profile 持久化与恢复链路

- 主要工作：为 profile navigation 增加手工顺序字段，并在 `App.tsx` 的初始化、刷新和 profile 切换时应用它。
- 预期成果：刷新、重启、切换 profile 后能稳定恢复文件树顺序。
- 执行顺序：在纯逻辑层稳定后接入。

阶段三：接入文件树拖拽重排交互

- 主要工作：为文件与文件夹节点补齐同级拖拽、插入位命中和 drop 提交；过滤视图下禁拖。
- 预期成果：用户能直接在完整树中拖动节点改变显示顺序，并看到明确插入反馈。
- 执行顺序：在排序模型可写可读后进行。

阶段四：补齐关联动作的顺序修正

- 主要工作：处理新建、删除、重命名、移动后的 order map 修正，并保持与隐藏、收藏、展开状态的兼容。
- 预期成果：文件树在各种节点操作之后仍保持稳定、可恢复的顺序。
- 执行顺序：拖拽交互完成后统一收口。

阶段五：补齐测试与浏览器验证

- 主要工作：新增纯逻辑测试、组件交互测试、App 恢复链路测试和浏览器实测。
- 预期成果：排序逻辑、交互边界和持久化恢复都可回归验证。
- 执行顺序：功能链路接通后统一回归。

### 3. 整体结构框架

本轮建议按五层组织：

- `src/workspace/file-tree-order.ts`
  - 承担手工顺序的纯逻辑：normalize、apply、move、rename、delete、cross-parent insert
- `src/workspace/file-tree.ts`
  - 继续只负责从路径生成基础树结构，不承担持久化和拖拽语义
- `src/workspace/profile-store.ts` / `server/project-profiles.mjs`
  - 承担 profile 中排序字段的读写与默认值兜底
- `src/App.tsx`
  - 承担读取排序配置、构建排序后树、在节点操作后修正顺序状态并写回 profile
- `src/app/WorkspaceLayout.tsx`
  - 承担文件树整行拖拽、插入命中态、过滤态禁拖和排序提交交互

## 现状证据

### 1. 当前文件树每次都按扫描路径重建，没有手工顺序层

当前 [file-tree.ts](/C:/Code/md-reader/src/workspace/file-tree.ts:8) 的 `buildFileTree(paths)` 只负责把 Markdown 路径数组转成目录树：

- 输入是真实路径数组
- 输出是 `FileTreeNode[]`
- 每层 `children` 的顺序完全来自构树时的插入顺序

这意味着：

1. 当前文件树并没有“用户手工顺序”的存储位置。
2. 只要刷新树，就会回到扫描顺序。
3. 若要支持固定化排序，必须在构树之后再叠加一层顺序应用逻辑。

### 2. 当前拖拽只支持“把文档拖入目录”，不支持同级重排

当前 [WorkspaceLayout.tsx](/C:/Code/md-reader/src/app/WorkspaceLayout.tsx:892) 已有一套文档拖拽状态：

- `dragDocumentPath`
- `dropDirectoryPath`
- `handleDocumentDragStart`
- `handleDirectoryDragOver`
- `handleDirectoryDrop`

但这套模型只有一个 drop 目标语义：拖入目录。

它缺少：

- 同级插入位置
- 文件节点作为排序锚点
- 根层节点排序
- 文件夹自身可拖排序
- 过滤态禁拖边界

所以本轮不能只是在现有 move-into-folder 上加一点视觉改动，而要新增“排序插槽”模型。

### 3. 当前 profile navigation 只保存展开、隐藏、收藏，不保存文件树顺序

当前 [profile-store.ts](/C:/Code/md-reader/src/workspace/profile-store.ts:17) 的 `WorkspaceProfile.navigation` 只包含：

- `expandedFileNodes`
- `expandedHeadingNodes`
- `hiddenPaths`
- `favoritePaths`

当前后端 profile 默认值 [project-profiles.mjs](/C:/Code/md-reader/server/project-profiles.mjs:23) 也是同样结构。

这意味着：

1. “按 profile 保存排序”是可以沿现有 `navigation` 继续扩展的。
2. 但必须补默认值、bridge 序列化和老 profile 兜底兼容。

### 4. 当前 `App.tsx` 已经承担树刷新和 profile/navigation 写回边界

当前 [App.tsx](/C:/Code/md-reader/src/App.tsx:1023) 已经负责：

- 读取 markdown paths
- `buildFileTree(markdownPaths)`
- 写入 `expandedFileNodes`
- 写入 `hiddenPaths` / `favoritePaths`
- 处理重命名、移动、删除后的路径状态修正

这说明排序持久化的最稳定落点不是 `WorkspaceLayout`，而是：

- `WorkspaceLayout` 只负责拖拽交互
- `App.tsx` 负责更新排序状态、重建树并写回 profile

这个边界和之前 `data-editor` 的 file-order 做法一致，稳定性更高。

## 需求收敛与关键决策

### 1. 同级允许完全自由混排

用户已经确认走“完全自由混排”：

- 文件夹和文档在同级内可以任意穿插
- 不保留“文件夹固定在前 / 文档固定在后”这类系统分组规则

这意味着排序模型必须以“直属子项 path 顺序”为核心，而不是分组内排序。

### 2. 排序结果按 profile 独立保存

用户已经确认顺序按 `profile` 保存：

- 同一项目在不同 profile 下可以有不同文件树顺序
- 排序属于 profile.navigation 偏好，而不是项目全局真相

这意味着：

1. 切换 profile 时，文件树顺序要跟着切换。
2. 排序字段应放在 `WorkspaceProfile.navigation` 下，而不是 localState 顶层。

### 3. 过滤视图内禁止排序

用户已经确认在搜索结果和“只看收藏”视图中不允许拖拽排序，只能在完整树里排序。

推荐理由：

1. 过滤视图只显示子集，用户难以理解“当前拖动到底改的是原树哪个父级”。
2. 搜索命中可能跨多个父目录，直接排序容易引入错误心智。
3. 禁拖后规则更清晰：过滤态负责查找，完整树负责组织。

### 4. 排序目标是 UI 顺序固定化，不改真实路径

与上次“拖入文件夹重组目录”的需求不同，这次排序明确是树内顺序固定化，不改变磁盘上的目录结构。

因此：

- 拖拽排序不调用 `moveDocumentNodeInBridge`
- 只改 profile 中的 order map
- 树刷新后按 order map 重排显示

## 方案设计

### 1. 排序数据模型

建议在 `WorkspaceProfile.navigation` 下新增字段：

```ts
manualNodeOrderByParent?: Record<string, string[]>
```

约定如下：

- key：父目录 path
- 根目录使用 `__root__`
- value：该父目录直属子项的完整 path 顺序

示例：

```json
{
  "__root__": ["项目文档", "temp", "docs", ".agents"],
  "项目文档/条目": [
    "项目文档/条目/条目.md",
    "项目文档/条目/专属条目",
    "项目文档/条目/机制条目",
    "项目文档/条目/非机制条目"
  ]
}
```

这个模型的优点：

- 与树结构天然一致
- 同时支持文件和文件夹混排
- 删除、重命名和真实跨目录移动后的修正范围清晰
- 可以对每个父目录独立 normalize / dedupe

### 2. 构树与排序应用链路

建议保持当前 `buildFileTree(paths)` 不变，再新增独立 helper，例如：

- `normalizeNodeOrderByParent(orderMap, tree)`
- `applyManualTreeOrder(nodes, orderMap)`
- `moveNodeInManualOrder(orderMap, payload)`
- `renameNodeInManualOrder(orderMap, sourcePath, targetPath)`
- `removeNodeFromManualOrder(orderMap, targetPath)`

应用顺序应为：

1. bridge 或 workspaceProvider 读取 markdown paths
2. `buildFileTree(markdownPaths)`
3. `applyManualTreeOrder(baseTree, manualNodeOrderByParent)`
4. `createVisibleFileTree(...)`
5. 传入 `WorkspaceLayout`

排序规则建议固定为：

- 先按手工顺序放入已知节点
- 未在顺序表里的新节点按原始扫描顺序补到末尾
- 顺序表里已失效的 path 自动剔除

### 3. 拖拽交互设计

拖拽交互建议沿用“整行可拖拽，不加 grip”的方向。

支持的排序场景：

- 根层节点之间自由重排
- 同一目录 children 之间自由重排

第一版明确不支持的排序场景：

- 通过“排序拖拽”把节点插入到另一个父目录下
- 通过“排序拖拽”改变目录树层级

原因是本轮排序目标只是 UI 顺序固定化，不改真实路径；一旦跨父目录插入，就会与真实目录层级冲突。跨目录调整位置仍应继续使用现有“真实移动文件/拖入文件夹重组目录”能力，而不是混入这次排序模型。

建议的命中模型：

- 拖到文件或文件夹行上半区：插到该节点前
- 拖到文件或文件夹行下半区：插到该节点后
- 拖到同一父级容器空白区：插到该父级末尾

建议的视觉反馈：

- 当前被拖节点维持现有 dragging 态
- 目标行显示上/下插入指示线
- 目标目录容器末尾显示尾插入槽位
- 搜索态 / 收藏态下禁拖时不出现任何 drop hint

### 4. 过滤态禁拖边界

以下情况统一禁止开始排序拖拽：

- 搜索 query 非空
- `showFavoritesOnly === true`

禁拖效果建议包括：

- `draggable={false}`
- cursor 不显示可拖语义
- 不渲染插入命中态
- 可选提示：状态栏说明“过滤视图中不能排序，请回到完整树”

过滤态显示规则需要明确：

- 搜索结果和“只看收藏”仍然基于完整树的手工顺序做投影显示
- 也就是说，过滤态不是另一套排序，只是不能在过滤态里修改顺序

### 5. 关联动作后的顺序修正

新建文档：

- 插入当前父目录顺序末尾

新建文件夹：

- 插入当前父目录顺序末尾

删除：

- 从所属父目录的顺序中移除
- 若被删除的是目录，还需清理其作为 parent key 的子顺序项

重命名：

- 保持同一父目录位置不变
- 将旧 path 替换成新 path
- 若重命名的是目录，还要同步改写其所有后代 path 和相关 parent key

真实移动到别的目录：

- 从旧父目录顺序移除
- 插入新父目录顺序末尾
- 若移动的是目录，还要同步改写整棵子树 path 引用

刷新扫描：

- 不覆盖现有手工顺序
- 对 order map 做 normalize 后再应用

### 6. 与现有状态的职责关系

建议职责边界固定为：

- `file-tree-order.ts`
  - 纯逻辑，不碰 React 状态
- `WorkspaceLayout.tsx`
  - 只处理拖拽生命周期、drop 事件和排序提交
- `App.tsx`
  - 读取/更新 `manualNodeOrderByParent`
  - 在刷新、节点操作、profile 切换时统一修正并写回
- `profile-store.ts` / `project-profiles.mjs`
  - 负责持久化格式与默认值

这样可以避免把排序逻辑散落到组件事件里，后续测试也更容易拆。

## 风险与约束

### 1. 目录重命名/移动的 path 级联修正是最大风险点

如果目录 path 变化，只替换目录自身而不改后代 path，会导致：

- 子目录顺序 key 失效
- 顺序表引用旧 path
- 展开/隐藏/收藏等状态断裂

因此目录级 rename/move 必须做整棵子树 path rewrite。

### 2. 过滤态显示的是投影，不是真实排序上下文

如果强行允许过滤态排序，会产生“当前看到的顺序”和“真实父目录顺序”不一致的问题。这个边界已经在方案里明确禁掉，后续实现不能回退。

### 3. 老 profile 兼容要走兜底默认值

已有 profile 没有 `manualNodeOrderByParent` 字段，因此：

- 前端读到 `undefined` 时必须视为空 map
- 后端默认 profile 也要补齐该字段
- normalize helper 不能假设字段一定存在

## 验证口径

纯逻辑测试：

- 顺序表 normalize / dedupe
- 根层与子层 apply order
- 同父级 move
- 跨父级 move
- rename / delete / create 后 order map 修正

组件测试：

- 完整树中节点可拖拽
- 搜索态和收藏态禁拖
- 上半区/下半区插入位命中正确
- 目录末尾空白区尾插入命中正确

App 级测试：

- profile 持久化恢复
- 切 profile 后顺序隔离
- 刷新树后顺序不丢
- 重命名/移动/删除后顺序仍保持合理

浏览器验证：

- 根层排序
- 同目录排序
- 新建后出现在末尾
- 刷新页面后顺序保留
- 切换 profile 后切换到对应顺序

## 待确认项

当前还剩一个产品决策没有锁死，但不影响本方案成立：

- 如果未来提供“重置当前 profile 导航偏好”的动作，是否要把手工文件树顺序一起清空？

当前建议是“要一起清空”，因为这份顺序属于 `navigation` 范畴，不应作为额外例外保留。
