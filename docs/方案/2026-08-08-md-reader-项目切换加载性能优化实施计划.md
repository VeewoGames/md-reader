>

## 方案概述

### 1. 总体目标和范围

本计划将已冻结的“持久化文件树快照 + 服务端单飞刷新链 + 前端原子项目切换”方案落成可分阶段验收的实现，使 Nocturnel 在存在有效快照时的项目切换文件树可交互 P95 不超过 300 ms，同时保证缓存不会覆盖真实文件变更、快速切换不会持久化错误项目、后台缺失观察不会销毁草稿或导航偏好。

范围包含：服务端快照与刷新协调器、`prefer-cache/wait/force` bridge 协议、节点操作的增量快照更新、前端项目切换状态机、latest-wins 持久化、missing provenance、项目强制刷新、自动化测试、性能基准、真实浏览器验证和编号文档同步。

不包含：缩小 Markdown 扫描范围、复用 `hiddenPaths` 作为扫描过滤、常驻文件 watcher、正文内容缓存、压缩 `manualNodeOrderByParent`、支持多个 bridge 进程共享同一 runtime home、修改 Nocturnel 仓库内容，或清理当前工作区的既有未提交修改。

### 2. 各阶段任务概要

1. **实施前边界冻结**：记录当前脏工作区、建立定向测试基线并确认冲突文件的所有权；预期成果是后续改动不会覆盖滚动恢复等既有工作。
2. **服务端快照核心**：实现 canonical paths、稳定 revision、持久快照、刷新链、generation、epoch/CAS 和全局扫描调度；预期成果是缓存核心可以脱离 HTTP 与 UI 独立证明正确。
3. **bridge 协议与节点操作**：接入 `200/202 + refreshId`、`wait`、`force` 和节点响应联合；预期成果是服务端成为扫描唯一 owner，内部文件操作无需整树重扫。
4. **前端原子切换与权限收口**：接入状态机、latest-wins、后台对账、missing provenance 和手动刷新；预期成果是用户得到即时且不会串项目的切换体验。
5. **端到端验收与文档同步**：完成基准、真实浏览器、构建、编号文档和差异检查；预期成果是性能与正确性证据可以独立复跑。

执行顺序严格为“边界冻结 → 缓存核心 → bridge 集成 → 前端集成 → 端到端验收”。阶段一、二的服务端门未通过前，不开始前端状态机；前端定向测试未通过前，不以真实浏览器观感替代正确性验证。

## 已冻结实施合同

- 磁盘文件系统是文档内容与存在性的最终 authority；快照只是导航投影。
- 服务端是普通后台扫描的唯一 owner；前端只按 `refreshId` 等待既有刷新链。
- `prefer-cache` 无完整快照时立即返回 `202 indexing`，不能等待扫描完成后才反馈。
- `force` 必须创建不早于点击时刻的 scan generation，不能复用过早扫描并声称刷新成功。
- 扫描发布受 `mutationEpoch` CAS 保护；磁盘快照写入还受项目级队列和 rename 前 revision/epoch CAS 保护。
- 快照保存、接口返回和 hash 输入共用同一个 `canonicalizeTreePaths()` 结果。
- 无完整快照时，节点操作只能返回 `treeStatus: dirty`，不能制造部分完整快照。
- 目标工作区准备成功后才持久化 active project；持久化成功后才提交前端 `activeProjectId`。
- 项目切换采用串行 commit lease：进入 active project 持久化前必须再次确认自己是最新待提交意图；一旦开始持久化，该事务必须完成 UI 提交，更新意图只能排队，不能让 registry 与 UI 分裂。
- 扫描或普通读取 404 只能产生 `observed-missing`；只有节点删除成功或用户确认产生 `confirmed-delete` 破坏性权限。
- 30 秒是由下一次 `prefer-cache` 请求触发的最短校验间隔，不是定时后台轮询。

## 阶段一：实现服务端文件树快照核心

### 涉及文件

- 新增 `server/project-tree-cache.mjs`
- 调整 `server/project-scanner.mjs`
- 新增 `tests/server/project-tree-cache.test.ts`
- 扩展 `tests/server/project-scanner.test.ts`

### 任务 1.1：建立 canonical paths 与稳定身份

1. 从 scanner 导出并复用单一 `isMarkdownFile()` 或等价规则。
2. 实现 `canonicalizeTreePaths()`：统一 POSIX 分隔符、过滤 `.md/.mdx`、去重，并保持当前“深度优先、同层路径排序”合同。
3. 以规范化 `rootPath + contentRoots` 计算安全 `projectFingerprint`；缓存文件名只使用 fingerprint hash。
4. 对 `version + projectFingerprint + canonical paths` 计算 SHA-256 `snapshotRevision`。
5. 区分 `generatedAt` 和 `lastVerifiedAt`；节点增量更新不能推进 `lastVerifiedAt`。

完成条件：同一集合不受输入顺序和重复项影响，跨重启得到相同 paths 与 revision；不同项目根或内容根不能命中同一快照。

### 任务 1.2：建立缓存 entry 与持久化边界

1. 定义内存 entry：完整快照、`mutationEpoch`、dirty 状态、当前刷新链、持久化写队列和最后验证时间。
2. 从 `%APPDATA%/md-reader/cache/project-trees/<fingerprint>.json` 读取快照；schema、fingerprint 或 `complete` 不合法时 fail-closed。
3. 使用唯一临时文件和同目录替换持久化；项目 mutation 与最终 CAS/rename 共用同一个项目级提交互斥区，每个写任务捕获 epoch/revision，rename 前再次 CAS。
4. 写入失败保留内存最新快照并标记 persistence dirty；不能删除可读取的上一版，也不能把缓存失败冒充节点操作失败。

完成条件：故障注入可以证明半写文件不被使用、旧写任务不能覆盖新 revision、服务重启恢复最新完整快照；必须覆盖“旧写通过初次 CAS 后、rename 前发生 mutation，随后进程终止”，并证明重启不会恢复旧快照。

### 任务 1.3：建立刷新协调器

1. 每个项目同一时刻最多一个扫描 Promise 和一个稳定 refresh chain；全局扫描并发上限为 1。
2. `prefer-cache` 超过 30 秒时创建/复用普通刷新链；无快照时创建首次索引链。
3. `force` 分配 `requestedGeneration`；只接受不早于该 generation 的扫描。
4. 扫描捕获 `mutationEpoch`；发布前不相等时丢弃结果，并让原 `refreshId` 继续等待重扫。
5. 前台首次索引和 force 优先于后台校验；不扫描预热全部注册项目。
6. refresh chain 的成功或失败终态由缓存核心保留 5 分钟；同一 `refreshId` 允许多个 waiter 重复读取同一终态。采用请求触发的惰性清理并限制每个进程最多保留 128 条终态记录，超限时先清理已过期项，再按最早完成顺序淘汰；运行中的 chain 不得被淘汰。

完成条件：并发请求只形成一条正确刷新链；force 不接受过早扫描；节点变更期间的扫描不会发布到内存或磁盘。

### 涉及文件

### 任务 2.1：冻结 tree 线协议

1. 实现 `mode=prefer-cache|wait|force`；拒绝未知 mode、跨项目/过期 `refreshId`。
2. `prefer-cache` 命中时返回 `200 { status: ready, tree, refreshId }`；未命中时立即返回 `202 { status: indexing, refreshId }`。
3. `wait` 只等待指定刷新链；CAS 冲突后的重扫仍归属同一 refreshId。
4. `force` 立即返回 `202 { status: refreshing, refreshId, requestedGeneration }`。
5. 扫描链失败返回 `503 TREE_REFRESH_FAILED`；旧缓存保留，但不能标为 fresh。
6. 在 `local-bridge-access` 和 provider 中新增返回完整判别联合的接口；阶段二保留旧 `string[]` 调用面的临时开发适配器，确保当前 App 与测试仍可编译。阶段三原子迁移全部调用方与 mocks 后立即删除适配器，最终产物不保留旧机制兼容层。

完成条件：客户端能在一次网络往返内区分 ready/indexing，并且不会拥有启动第二轮后台扫描的能力。

### 任务 2.2：接入节点增量更新

1. 复用 canonical Markdown 判断处理新建、复制、删除、移动和改名；覆盖 `.md/.mdx` 与其他扩展名互转。
2. 磁盘操作成功后递增 `mutationEpoch`；只有完整快照可做 add/remove/rewrite。
3. 节点响应返回 `NodeMutationResponse`：`updated + tree` 或 `dirty + null`。
4. 删除成功返回单次使用、响应局部有效的 `confirmed-delete` capability，并绑定 `projectFingerprint + path + mutationEpoch + workspaceLoadRevision`；路径重建、mutation/revision 变化或响应过期后必须失效，普通 404 不生成该能力。
5. 缓存 patch/持久化失败时节点磁盘操作仍返回成功，并将 tree 标记为 dirty。

完成条件：内部节点操作不再触发无必要全树扫描；没有完整快照时不会返回伪完整 tree；扩展名转换与下一次强制扫描一致。

### 任务 3.1：建立切换状态机与写锁

1. 增加 `pendingProjectId` 和显式状态：`ready`、`switching`、`indexing`、`cache-ready`、`reconciling`、`refresh-failed`。
2. switching/indexing 保留旧工作区只读显示，锁定保存、节点操作和其他项目写动作；状态提示在选择后 100 ms 内可见。
3. cache hit 时准备目标 profile、tree、local state、session 和活动文档；全部成功后进入 active 持久化。
4. cache miss 的 `202` 立即进入 indexing，再通过 `wait(refreshId)` 取得目标 tree。
5. 失败时清除 pending、恢复旧下拉框显示和写权限，旧 `activeProjectId` 始终保持 authority。
6. 新增无副作用的 `prepareWorkspaceSnapshot()`（或等价职责）：准备期间不得修改 loading、tree、tab、history 或清理 404 文档；只在最终 commit 一次性应用结果。不得直接复用当前会立即写 UI/触发 purge 的 `loadDocumentContent()` 作为 prepare。

完成条件：UI 显示的 pending/active 身份和写入目标不会错配；冷加载期间无法把操作写到旧项目或半准备目标。

### 任务 3.2：建立 revision 与 latest-wins 提交门

1. 每次项目/Profile 切换递增 `workspaceLoadRevision`，捕获 `projectId + profileId + revision`。
2. 守卫成功、404、异常、profile/local state 写入、history 和 `finally`；迟到结果不得清理新请求状态。
3. 目标工作区准备成功后进入串行 commit lease；真正调用 `setActiveProject()` 前再次确认它仍是最新待提交意图，已被替代且尚未开始持久化的事务直接退出。
4. 一旦 `setActiveProject()` 开始，该事务取得不可撤销的 commit lease：持久化成功后必须原子提交对应 `activeProjectId` 和目标工作区；更新意图排队等待，不能仅因 revision 更新而拒绝本次 UI commit。
5. 快速 A → B → A 合并尚未进入持久化的中间意图；已进入持久化的事务按序完成 UI commit，再继续最新排队意图。若后续意图准备失败，最终 UI 与 registry 保持在最后一次成功事务。
6. 显式覆盖“当前 X，B 已开始持久化，随后选择 A，A prepare 失败”：最终必须是 B/B，不能出现 registry=B、UI=X。

完成条件：延迟成功、404、异常和 finally 均不能覆盖最新选择；registry 与 UI 最终项目一致。

### 任务 3.3：接入后台对账、missing provenance 与节点响应

1. ready 响应带 `refreshId` 时只调用 `wait`，不启动新扫描；revision 未变不重建树。
2. 后台缺失将打开文档标为 `observed-missing`，保留 tab、dirty draft、收藏、manual order 和 local state。
3. observed-missing 文档随后读取 404 仍保持 orphan；只有 `confirmed-delete` 或用户明确确认可调用 purge。
4. 节点操作 `updated` 直接应用 tree；`dirty` 按已确认路径做局部 UI 更新并提示等待校验，不追加默认 tree 请求。
5. 在 TopBar 增加“刷新项目”，调用 force 后等待 refreshId；提供 pending、成功、失败和重试反馈。
6. 删除菜单文字固定为“删除文档”，同步更新旧测试的可访问名称断言，不把措辞变化扩散到删除 authority。

完成条件：后台对账不造成草稿或导航数据丢失；节点操作不触发整树扫描；手动刷新得到不早于点击时刻的结果。
