# md-reader 项目切换加载性能优化方案

> 状态：已实施并完成自动化、构建及真实 Chrome 切换验收（2026-08-08）。

## 方案概述

### 1. 总体目标和范围

目标是消除大型 Markdown 项目在重复切换时的整库同步扫描等待，让用户选择 Nocturnel 后可以立即看到目标项目状态和最近一次可用文件树，同时在后台完成最新文件状态校验。

本轮采用“持久化文件树快照 + 内存单飞刷新 + 前端后台对账”的路线。缓存只改变文件树索引的获取时机，不改变 Markdown 文件的读取 authority：打开文档时仍由本地服务从项目目录读取真实文件；强制刷新仍会重新扫描磁盘。

本轮包含：服务端项目文件树缓存合同、冷/热加载路径、后台刷新与单飞控制、应用内文件操作后的缓存同步、外部文件变化对账、前端项目切换竞态保护、加载状态反馈，以及量化性能与正确性验证。

本轮不包含：缩小 Nocturnel 的 Markdown 可见范围、将 UI `hiddenPaths` 当成扫描排除规则、引入常驻文件系统 watcher、重构文档内容缓存、优化 `.md-reader/profiles.json` 体积，或改变项目/Profile 的状态归属。

### 2. 各阶段任务概要

1. **冻结文件树快照合同**：定义缓存身份、数据结构、命中状态和失效规则；预期成果是缓存不会成为第二套文件 authority。
2. **建立服务端缓存与刷新链**：加入持久化快照、内存单飞任务和强制刷新能力；预期成果是重复切换立即返回缓存，首次无缓存时仍能可靠建立索引。
3. **接通前端即时切换与后台对账**：并行读取 profile/文件树，以项目加载修订号隔离迟到响应；预期成果是项目选择即时反馈，旧项目结果不会覆盖新项目。
4. **收口文件操作与外部变化**：应用内路径变更精确更新缓存，外部变化由后台刷新和手动刷新收敛；预期成果是性能优化不牺牲文件树正确性。
5. **执行性能与体验验收**：覆盖缓存合同、竞态、冷/热路径和真实 Nocturnel 切换；预期成果是热切换达到量化目标，冷加载状态清晰且 UI 不假死。

执行顺序必须先定义缓存真值与失效边界，再建立服务端缓存，随后接入前端异步对账，最后验证真实体验。不能先在 UI 层保存一份无版本文件树再补正确性规则。

### 3. 整体结构框架

```text
用户选择项目
    │
    ├─► 立即更新 pendingProjectId 与切换反馈
    │
    └─► GET /tree（prefer-cache）
           │
           ├─ 有可用快照 ─► 立即返回 paths + snapshotRevision
           │                    │
           │                    └─► 后台扫描 / 单飞对账
           │                              │
           │                              └─► 新 revision 仅更新当前项目
           │
           └─ 无可用快照 ─► 同步首次扫描 ─► 原子写入快照 ─► 返回

应用内新建 / 删除 / 改名 / 移动
    └─► 磁盘操作成功后精确更新快照 revision

用户手动刷新
    └─► force-refresh ─► 等待真实扫描 ─► 原子替换快照
```

## 已验证现状与根因

### 1. 现场性能证据

2026-08-08 在同一运行中的本地服务 `127.0.0.1:8797` 上测得：

| 项目/步骤 | 耗时 | 结果规模 |
| --- | ---: | ---: |
| Nocturnel 文件树接口 | 约 2,351 ms | 5,744 条路径，约 482 KB |
| Neon Race 文件树接口 | 约 46 ms | 30 条路径 |
| Nocturnel profile 列表 | 约 6 ms | 2 个 Profile |
| Nocturnel profile 内容 | 约 6 ms | 1 个 Profile |
| 前端树构建、排序、隐藏过滤 | 约 15–25 ms | 5,744 条路径 |

因此当前主要等待来自服务端磁盘扫描，不是下拉框、profile 请求或 React 文件树构建。

### 2. 当前调用链

项目切换依次执行：

1. `workspaceProvider.setActiveProject()` 持久化活动项目；
2. `loadLocalServiceProject()` 调用 `getFileTreePaths()`；
3. 文件树完成后才读取 profile、恢复 local state、构建会话；
4. 最后读取活动文档内容。

服务端 `/api/projects/:projectId/tree` 每次请求都直接调用 `scanMarkdownTree()`。扫描器从每个 `contentRoots` 递归 `readdir()`，且目录之间串行等待；当前项目注册统一使用 `contentRoots: ["."]`。

### 3. Nocturnel 扫描放大来源

扫描器目前只跳过 `.git`、`node_modules` 和 `.md-reader`。Nocturnel 中以下目录即使最终在 UI 中被隐藏，仍会先被完整遍历：

| 一级目录 | 文件数 | Markdown 数 |
| --- | ---: | ---: |
| `temp` | 51,918 | 2,625 |
| `.godot` | 42,344 | 0 |
| `tools` | 16,732 | 137 |
| `assets` | 11,926 | 0 |
| `项目文档` | 1,161 | 1,139 |
| `docs` | 1,203 | 1,005 |

`hiddenPaths` 是用户可切换显示的导航偏好，不是扫描配置。若直接用它跳过目录，“显示隐藏内容”将无法恢复这些文档，因此不能把 UI 隐藏与扫描排除混为同一机制。

## 推荐目标设计

### 1. authority 与一致性边界

- **磁盘文件系统**：文档存在性与内容的最终 authority。
- **文件树快照**：某一时刻磁盘扫描结果的可复用投影，只负责快速导航。
- **前端文件树**：服务端快照的当前显示投影，不独立持久化为新的 authority。
- **文档读取**：始终按项目、Profile 和路径通过现有服务端安全边界读取；快照中存在路径不保证文件此刻仍存在。

缓存命中允许短暂陈旧，但必须可观察、可后台收敛、可手动强制刷新。读取缓存失败、schema 不兼容或身份不匹配时必须 fail-closed，退回首次扫描，不能猜测或拼接旧结果。

### 2. 快照身份与存储

新增服务端模块，例如 `server/project-tree-cache.mjs`，将快照放在运行时目录而不是项目仓库：

```text
%APPDATA%/md-reader/cache/project-trees/<projectFingerprint>.json
```

建议快照结构：

```json
{
  "version": 1,
  "projectId": "nocturnel-7dba4304",
  "projectFingerprint": "<rootPath + contentRoots hash>",
  "snapshotRevision": "<stable content hash>",
  "generatedAt": "<ISO timestamp>",
  "lastVerifiedAt": "<ISO timestamp of latest complete scan>",
  "complete": true,
  "paths": ["docs/README.md"]
}
```

`projectFingerprint` 必须包含规范化 `rootPath` 与规范化、排序后的 `contentRoots`，缓存文件名只能使用该 hash，不能直接信任可人工编辑 registry 中的 `projectId`。项目 ID 相同但根目录或内容根发生变化时，旧快照不得命中。

`snapshotRevision` 固定为稳定内容 hash。新增共享纯函数 `canonicalizeTreePaths()`，复用 scanner 的 Markdown 扩展名和既有深度/路径排序规则，生成规范化、去重、排序后的唯一 `paths`；快照存储、接口返回和 SHA-256 输入必须使用同一个数组，再连同 `version` 与 `projectFingerprint` 计算 hash。相同文件树跨扫描、跨进程重启必须得到相同 revision；`generatedAt` 或 `lastVerifiedAt` 变化不改变 revision。只有 `complete: true` 的全量快照允许被 prefer-cache 使用。

`generatedAt` 表示当前快照内容最后一次因扫描或应用内节点变更生成的时间；`lastVerifiedAt` 只在完整扫描成功发布时更新。30 秒校验间隔使用 `lastVerifiedAt`，节点增量更新不得伪装成已检查其他外部变化。

写入采用唯一临时文件加同目录原子替换，避免服务中断留下半份 JSON。每个项目只有一个持久化写队列，写任务携带捕获的 `mutationEpoch + snapshotRevision`；执行 rename 前必须再次确认二者仍与内存当前版本相同，旧写任务直接丢弃，禁止晚完成的扫描覆盖较新的节点变更。Windows 覆盖行为必须通过故障注入测试；替换失败时保留内存快照并标记持久化 dirty，不删除仍可读取的上一版文件。

### 3. 文件树读取合同

文件树接口固定为：

```text
GET /api/projects/:projectId/tree?profileId=:profileId&mode=prefer-cache|wait|force
```

- `prefer-cache` 是普通加载唯一允许启动扫描的 owner。有完整且 fingerprint 匹配的快照时立即返回 `200`；`lastVerifiedAt` 超过 30 秒时同时启动或复用一轮后台扫描，并在响应中携带 `refreshId`。没有完整快照时立即启动或复用首次扫描，并返回 `202 { status: 'indexing', refreshId }`，不能阻塞到扫描完成后才让前端知道 cache miss。
- `wait&refreshId=:refreshId` 只等待服务端已创建的指定刷新链，不得自行启动第二轮扫描。若 epoch/CAS 冲突导致扫描结果被丢弃，该 refreshId 必须继续关联后续重扫，直到得到可发布结果或明确失败。
- `force` 是手动刷新唯一允许启动强制代际的入口。请求分配 `requestedGeneration` 并立即返回 `202 { status: 'refreshing', refreshId, requestedGeneration }`。它只能接受 `scanGeneration >= requestedGeneration` 的扫描；若当前扫描开始得更早，必须在其结束后再排一轮，不能把过早扫描声称为手动刷新结果。

`prefer-cache` 的响应联合为：

```ts
type ProjectTreeLookupResponse =
  | { status: 'ready'; tree: ProjectTreeResponse; refreshId: string | null }
  | { status: 'indexing'; refreshId: string }
```

成功响应固定为判别联合，不允许 provider 把元数据收窄成 `string[]`：

```ts
type ProjectTreeResponse = {
  paths: string[]
  snapshotRevision: string
  generatedAt: string
  source: 'cache' | 'scan'
  freshness: 'stale' | 'fresh'
  refreshing: boolean
}
```

`wait` 扫描失败返回 `503 TREE_REFRESH_FAILED`；已有缓存继续留在内存和 UI 中，但失败响应不能伪装成 fresh。`prefer-cache` 只有在完整快照可验证时才允许返回 stale；无快照且首次扫描失败时返回错误，不拼接部分结果。`refreshId` 必须绑定 project fingerprint 和刷新链，未知、过期或跨项目使用返回受控错误。

接口需要显式区分以下状态：

| 状态 | 服务端行为 | 前端行为 |
| --- | --- | --- |
| `cache-hit` | 立即返回快照；仅超过 30 秒校验间隔时启动或复用后台刷新并返回 `refreshId` | 立即显示文件树；有 `refreshId` 时等待同一刷新链 |
| `cache-miss` | 立即返回 `202 + refreshId`，后台执行首次扫描 | 100 ms 内显示“首次建立索引”，再通过 `wait` 等待 |
| `refreshing` | 同项目只保留一个扫描 Promise 和稳定刷新链 | 按 `refreshId` 加入同一次刷新，不启动新扫描 |
| `fresh` | 返回本轮扫描 revision | 仅当项目仍为当前目标时应用 |
| `cache-invalid` | 隔离无效快照并重新扫描 | 不展示无法验证的旧数据 |

接口响应必须携带 `snapshotRevision`、`generatedAt`、`source`、`freshness` 和 `refreshing`。前端不能仅凭数组内容猜测缓存状态。

### 4. 后台刷新与单飞规则

1. 同一项目在任意时刻最多运行一个真实扫描任务；多个切换、刷新或对账请求由服务端加入同一刷新链。所有项目共享全局并发上限 1，前台切换/手动刷新优先于后台对账。
2. 每个项目缓存 entry 持有递增 `mutationEpoch`。扫描开始时捕获 epoch；扫描完成发布前必须再次相等。期间发生应用内节点变更时，旧扫描结果直接丢弃并排队重扫，禁止覆盖增量更新后的快照；原 refreshId 的等待者继续等待重扫结果。
3. 缓存命中后前端先应用快照；仅当 `prefer-cache` 返回非空 `refreshId` 时调用 `wait`，前端不得拥有后台扫描启动权。返回 revision 不变时不重建文件树。
4. 后台结果必须完整扫描成功、fingerprint 未变且 epoch 校验通过后才替换快照；扫描失败保留上一个可用快照，并显示非阻塞提示。持久化写入还必须通过项目级写队列和 rename 前版本 CAS。
5. 手动“刷新项目”使用 `force` 创建强制 generation，再通过返回的 `refreshId` 等待不早于本次点击开始的扫描；完成前不得声称文件树已是最新。
6. 首版不启动“扫描全部注册项目”的服务预热。服务启动只读取持久快照元数据，实际项目在首次访问时按前台优先规则校验，避免多个大型项目争抢磁盘。
7. 首版不引入常驻 watcher。30 秒只是下一次 `prefer-cache` 请求允许重新校验的最短间隔，不是定时器；用户停留在同一项目且不再触发 tree 请求时，外部变化只能由手动刷新收敛。

### 5. 应用内文件操作后的缓存更新

由 md-reader 发起且已成功落盘的操作具有精确路径信息，不应再为了单个变更扫描整个 Nocturnel。增量更新只允许作用于 fingerprint 匹配且 `complete: true` 的快照；没有完整快照时仅递增 `mutationEpoch` 并保持 cache-miss/dirty，不能从空集合制造“完整快照”。

节点操作与扫描必须复用同一 Markdown 扩展名判断：

- 新建/复制 `.md`/`.mdx`：向快照插入规范路径；其他扩展名不进入快照；
- 删除 `.md`/`.mdx`：从快照移除目标路径；其他扩展名不改变快照；
- `.md/.mdx → .md/.mdx`：原子重写路径；
- `.md/.mdx → 其他扩展名`：移除源路径；
- 其他扩展名 `→ .md/.mdx`：加入目标路径；
- 其他扩展名之间改名/移动：不改变快照；
- 新建目录：Markdown 路径集合不变；
- 操作失败：不得修改快照。

缓存更新和磁盘写入不组成跨文件系统事务，因此顺序固定为“磁盘成功 → 递增 `mutationEpoch` → 更新完整内存快照 → 加入持久化队列”。节点响应固定为联合类型：

```ts
type NodeMutationResponse =
  | { node: BridgeNodePayload; treeStatus: 'updated'; tree: ProjectTreeResponse }
  | { node: BridgeNodePayload; treeStatus: 'dirty'; tree: null }
```

`updated` 时前端直接应用 tree，不再调用默认会触发后台对账的 `getFileTreePaths()`；`dirty` 时保留当前前端树，按已确认节点操作做局部 UI 更新并显示“等待文件树校验”，不得假造完整快照。缓存更新或持久化失败只影响索引状态和下次启动速度，不得把已经成功的文件操作回滚或误报为文档写入失败；服务端标记 dirty，并在下次 `prefer-cache`/force 时重建。

### 6. 前端项目切换与竞态保护

`App` 增加单一递增的 `workspaceLoadRevision` 和独立 `pendingProjectId`。每次项目/Profile 切换捕获目标 `projectId + profileId + revision`，所有异步结果及副作用在提交前验证三者仍为当前值。守卫范围必须覆盖成功提交、失败提示、404 purge、local state/profile 写入、history 更新和 `finally` 中的 loading 清理。

服务端活动项目写入不能仅依赖前端 revision。目标 profile、tree、session 和活动文档全部准备成功且 revision 仍有效后，客户端才将 `setActiveProject()` 放入单一串行 latest-wins 队列；服务端持久化成功后再原子提交前端 `activeProjectId`。快速 A → B → A 可以合并尚未开始的中间请求，已开始的请求按顺序完成，最后一次持久化必为 A。准备或持久化失败都保留旧项目，不执行目标 UI 提交；刷新页面后必须恢复最后一次成功选择。

项目切换状态机固定为：

| 状态 | 可见内容 | 写操作 |
| --- | --- | --- |
| `ready` | 当前活动项目 | 正常开放 |
| `switching` | 旧工作区保留，并显示“正在切换至目标项目”遮罩 | 禁止保存、节点操作和其他会写入项目的动作；允许只读查看旧内容 |
| `indexing` | 无缓存时继续显示稳定外壳和首次索引进度 | 与 `switching` 相同 |
| `cache-ready` | 原子提交目标项目、profile、文件树和 session | 正常开放；后台 refresh chain 非阻塞 |
| `reconciling` | 目标缓存树保持可用 | 正常开放，但后台结果必须受 revision/epoch 守卫 |
| `refresh-failed` | 继续使用目标缓存树并显示警告 | 正常开放；提供重试 |

切换失败时回滚 `pendingProjectId` 和下拉框显示，旧 `activeProjectId` 与工作区继续作为唯一写入 authority。

前端加载顺序调整为：

1. 用户选择后立即设置 `pendingProjectId` 和“正在加载目标项目”状态，但不提前改变 `activeProjectId`；
2. 并行读取文件树快照与 project profile；
3. 快照返回后恢复目标 local state、标签和活动文档，全部准备完成后原子提交 `activeProjectId` 和目标工作区；
4. 后台 `wait` 结果只在 revision 仍有效时对账；
5. 后台扫描观察到路径缺失时只更新文件树，并将仍打开的缺失文档标记为 `observed-missing`；不得关闭标签、丢弃 draft、删除收藏、改写 local state 或修剪 manual order；
6. `reconcileLocalStateWithFileTree()` 仅用于首次恢复和已确认删除，不能直接用于后台观察结果；
7. missing provenance 必须贯穿后续文档读取：扫描或普通读取 404 只能维持 `observed-missing`；只有 md-reader 节点删除成功产生的 `confirmed-delete` capability，或用户明确确认“从工作区移除”，才允许调用 destructive purge；
8. 迟到的旧项目树、profile、文档成功/404/异常和 `finally` 全部丢弃，不能重新切回旧项目或清除新请求状态。

项目切换期间不应清空整页再等待扫描。缓存命中时直接切入目标工作区；缓存未命中时保留稳定外壳和明确的首次索引状态。

## 实施阶段

### 阶段一：建立可独立验证的快照模块

涉及：新增 `server/project-tree-cache.mjs` 及定向测试。

1. 定义快照 schema、fingerprint、`canonicalizeTreePaths()`、稳定内容 hash revision、`complete`、`lastVerifiedAt`、`mutationEpoch`、原子读写和损坏快照处理。
2. 实现项目级内存 cache entry、同项目 single-flight/refresh chain、跨项目全局单并发队列和前台优先级。
3. 冻结“扫描捕获 epoch、发布前 CAS 校验、冲突时沿同一 refreshId 重扫”的内存发布合同，以及“项目级写队列、rename 前 revision/epoch CAS”的持久化合同。
4. 复用现有 `scanMarkdownTree()` 作为唯一全量扫描入口，并导出/复用单一 Markdown 扩展名判定，不在此阶段改变目录可见范围。

完成条件：同项目并发请求只触发一次扫描链；有效快照可跨服务重启读取；错误 fingerprint/schema 不会被使用；扫描与节点变更并发不会向内存或磁盘发布旧结果；无完整快照时增量操作不会制造部分快照。

### 阶段二：接入 bridge 文件树与节点操作

涉及：`server/bridge-server.mjs`、`server/project-scanner.mjs`、节点操作路由及服务端测试。

3. 服务启动只读取持久快照元数据，不扫描全部注册项目；首次前台访问拥有扫描队列最高优先级。
4. 为响应加入缓存元数据、`TREE_REFRESH_FAILED` 和可诊断错误，不改变现有路径安全检查。
5. 增加扫描进行中并发 create/delete/rename、旧持久化写晚完成、无快照节点操作、`.md ↔ 非 Markdown` 转换、force 晚于扫描开始、refreshId 绑定和 Windows 原子替换失败等服务端测试。

完成条件：热路径在 30 秒校验间隔内不执行整库扫描；首次扫描和强制刷新结果与同一时点直接调用 scanner 得到的路径集合完全一致；内部文件操作无需全树重扫即可得到正确结果。

## 性能测量协议

1. 在切换入口记录 `project-switch-requested`；目标 `activeProjectId`、profile、文件树和 session 原子提交后，等待首个可交互 `requestAnimationFrame`，记录 `project-tree-interactive`。
2. “可交互”要求目标文件树已渲染、鼠标/键盘选择可用、切换遮罩已移除；只更新下拉框文本不算完成。
3. 热路径使用同一代码提交、Node/浏览器版本和本地服务进程；先预热 3 次，再在 Nocturnel 与 Neon Race 间交替切换 30 次，报告 P50、P95、max、路径数和响应字节数。
4. 服务重启后持久快照路径单独测 10 次；首次无快照使用隔离的 benchmark runtime home，不删除或覆盖用户正式缓存，记录扫描耗时、状态提示出现时间和浏览器主线程最长任务。
5. 同一提交先直接调用 scanner 建立冷扫描基线；经过缓存层的首次无快照完成耗时不得超过该基线的 `max(+10%, +200 ms)`。
6. 后台扫描期间持续执行标签切换与文件树点击；状态提示应在 100 ms 内可见，浏览器主线程不得出现由本功能新增的超过 100 ms long task，并记录交互响应 P95。
7. benchmark 只以脚本生成的 JSON 为正式证据；P95 固定使用排序后 `ceil(0.95 * n) - 1` 下标，禁止人工挑选样本。

## 量化验收标准

- [ ] 有持久快照时，从选择项目到 `pendingProjectId`、切换遮罩和目标项目名称反馈不超过 100 ms。
- [ ] 有持久快照时，从选择项目到目标文件树可用的本机 P95 不超过 300 ms。
- [ ] 30 秒校验间隔内的重复热切换不触发新的顺序全量扫描；跨项目扫描全局并发不超过 1。
- [ ] 无快照的首次加载允许执行完整扫描，但首次索引状态在 100 ms 内出现，旧工作区写操作被锁定，浏览器主线程不新增超过 100 ms long task。
- [ ] 无快照首次加载经过缓存层的完成耗时不超过同提交直接 scanner 基线的 `max(+10%, +200 ms)`。
- [ ] 后台刷新期间文件树操作、标签切换和已缓存文档阅读保持可用，不出现超过 100 ms 的本功能新增主线程 long task，交互响应 P95 不超过 100 ms。
- [ ] 服务重启后可以复用 fingerprint 匹配的持久快照，而不是退化为每次首次扫描。
- [ ] 后台结果 revision 未变化时不重建文件树，不造成目录展开、选择或滚动闪动。
- [ ] 快速 Nocturnel → Neon Race → Nocturnel 切换只应用最后一次选择的结果。
- [ ] 上述快速切换后刷新页面，仍恢复最后一次选择的 Nocturnel，而不是迟到 POST 写入的 Neon Race。
- [ ] 应用内新建、复制、删除、改名和移动后，文件树与磁盘结果一致且不执行无必要全树扫描。
- [ ] 扫描与节点操作并发时旧扫描不覆盖新路径；没有完整快照时不生成部分有效快照；`.md/.mdx` 与其他扩展名互转符合统一索引规则。
- [ ] 旧持久化写任务晚完成时无法覆盖更新 revision；服务重启后仍恢复最新快照。
- [ ] 外部新增/删除 Markdown 可由后台对账或手动刷新收敛。
- [ ] 后台发现打开文档缺失时保留标签、dirty draft、收藏、manual order 和 local state；确认删除才执行破坏性清理。
- [ ] `observed-missing` 文档随后读取返回 404 时仍保留上述状态；只有 `confirmed-delete` 或用户确认可 purge。
- [ ] 手动 force 不接受开始时间早于点击时刻的扫描结果。
- [ ] 损坏、不完整或 fingerprint 不匹配的快照不会被当作有效结果；仅时间较旧但身份完整的快照仍可作为 stale 显示并触发对账。
- [ ] `hiddenPaths`、“显示隐藏内容”、收藏、自由排序和当前 Profile 隔离行为不回归。

## 风险与控制

1. **缓存陈旧导致短暂显示已删除文档**：文档读取仍以磁盘为准；后台扫描和普通读取 404 只产生 `observed-missing`，不自动销毁草稿或导航偏好。
2. **旧项目异步结果覆盖新项目**：所有树、profile、文档、404、错误和 `finally` 由 `workspaceLoadRevision` 守卫；目标准备成功后才进入活动项目 latest-wins 持久化队列，成功后才提交 UI。
3. **扫描或旧持久化写覆盖节点增量更新**：项目级 `mutationEpoch` 是内存发布 CAS；项目级写队列和 rename 前 revision/epoch 校验保护磁盘快照。
4. **并发刷新放大磁盘压力**：服务端是扫描唯一 owner，按项目 single-flight refresh chain、跨项目全局并发 1、前台优先，并设置请求触发的 30 秒校验间隔；手动 force 创建不早于点击时刻的扫描代际。
5. **快照损坏或项目路径复用**：schema、fingerprint 与 `complete` 三重校验，写入使用原子替换；无效快照退回扫描。
6. **内部文件操作成功但缓存写入失败**：不回滚真实文件操作；内存标记 dirty，并以后台全量刷新修复持久快照。
7. **缓存优化掩盖扫描器长期扩展问题**：记录冷扫描基准；若 Nocturnel 继续增长导致后台扫描不可接受，再单独设计明确的 `scanExcludePaths` 或有界并发扫描，不在本轮隐式改变文档范围。

## 非目标与后续候选

- 不把 `.godot`、`temp`、`tools` 等目录直接硬编码为全局排除项；其中部分目录确有 Markdown 内容。
- 不复用 `navigation.hiddenPaths` 控制服务端扫描；隐藏内容仍必须可重新显示。
- 不在首版使用 `fs.watch`/`chokidar`。若后台对账频率无法满足外部编辑体验，再单独评估 watcher 的丢事件、重命名和大目录成本。
- 不在服务启动时扫描全部注册项目；持久快照读取不等同于预热扫描。
- 不支持多个 bridge 进程并发写同一个 runtime home；正式生命周期保持单 owner，若未来需要多实例必须另立跨进程锁方案。
- 不在本轮压缩 `manualNodeOrderByParent`。当前 profile 文件较大，但现场 profile 请求与前端排序并非主要等待来源。
- 不缓存 Markdown 正文；正文保存、冲突检测和读取 authority 保持现状。

## 进入开发前的门槛

本方案已采用“缓存优先、后台刷新”作为推荐路线，但方案文档本身不等同于运行时代码实施授权。进入开发前应再次确认以下决策：

1. 接受热切换先显示最近快照、随后后台收敛的短暂陈旧窗口；
2. 接受后台观察到缺失时不自动删除 dirty tab、收藏和 local state，由确认删除或用户操作收口；
3. 接受首版不使用常驻文件 watcher，也不扫描预热全部注册项目；
4. 接受持久快照写入 `%APPDATA%/md-reader/cache`，不写入项目仓库；
5. 接受稳定内容 hash、`mutationEpoch` 内存 CAS、持久化写前 CAS、串行 latest-wins 和请求触发的 30 秒校验间隔；
6. 接受服务端作为扫描唯一 owner，以 `202/refreshId/wait` 传递首次索引和后台刷新状态，force 使用独立 generation；
7. 接受 missing provenance，只有 `confirmed-delete` 或用户确认拥有破坏性清理权限；
8. 性能目标按本文测量协议，以本机 P95 300 ms 文件树可交互为首版门槛。
