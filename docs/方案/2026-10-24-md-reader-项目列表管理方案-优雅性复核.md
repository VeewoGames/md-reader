# 项目列表管理方案优雅性复核

> 日期：2026-10-24。对象：[项目列表管理方案](./2026-10-24-md-reader-项目列表管理方案.md)。本报告是方案审查结果，不是功能验收或实施授权。

## 审查结论

**修订后可进入实施计划细化。** 架构代理与独立 recheck reviewer 先审查初稿，再复审关键修订的可行性；主代理将确认的问题与补充约束合入方案，并进行最终文档一致性检查。没有发现值得整体重构的冗余；初稿的三个正确性缺口已补齐合同。多进程 writer 与路径身份的事实检查点仍须在实施前完成，不据此宣称方案已经通过运行验证。

## 需求与架构依据状态

已确认的最小需求为：当前 Profile 接入已有项目、持久化自由排序、仅注销登记、允许直接移除当前项目并安全切换、允许最后清空。快速切换、未保存保护、草稿归属和跨 Profile 隔离必须保持。

ADR 0022 将本机接入列表与项目内配置分层；ADR 0023 要求当前 Profile 在无 active 时仍可见。方案继续沿用这两个边界，并把首次携带项目与已清空列表的区别纳入 ADR 0022 的后续补充范围，不擅改当前 Truth。

## 已确认问题与处理

| 初稿问题 | 影响及证据 | 已合入的最小修正 |
|---|---|---|
| 未区分未初始化与已清空 Profile | `App.tsx:1746` 遇到无 active 会自动注册当前项目，用户清空结果可能被覆盖 | 主方案 2.1、2.2、4.2：由合法 projects 数组派生 initialized，首次携带仅用于未初始化；清空后保留业务记录；增加清空后跨 Profile 返回测试 |
| 将 GET 对账当作原 mutation 已结束 | 一次旧快照不能排除原 POST 随后落盘，解除保护后仍可能被迟到请求修改 | 主方案 3.3：窄 reconcile 命令在同一文件事务内推进旧版本或读取已推进版本，使迟到请求失效；不引入命令日志 |
| 旧 active 修复的落盘时点含糊 | 初稿同时描述内存补齐与修复升版本，可能发布未持久化的快照 | 主方案 2.1、2.3：缺省 revision 可归一化；实际 active 修复必须事务落盘成功后返回，失败报错 |

修订的二次检查又发现初始化判断与协调占位之间的表示歧义，已统一为两种内部记录：未初始化协调占位 `{revision}`；已初始化记录 `{revision, projects, activeProjectId}`。GET 只做投影，不给占位补写业务字段；register 继承版本再递增，active 修复不作用于占位。兼容性明确限定为新版读取旧数据，不声称旧版 writer 可以理解新形态。

## 复用与架构评估

- **单一数据结构：** projects 数组即顺序。删除额外 sortIndex、排序文件或浏览器长期副本，不损失当前需求，减少一致性维护。
- **沿用现有链路：** registry、bridge、provider、App 和界面各有既有职责，不为本功能再建应用服务层、事件总线或通用 mutation 平台。
- **动作复用：** 添加后打开与当前项目移除复用 dirty gate、prepare 和 commit。只提取已有真实调用路径共享的部分，不建设第三套会话状态机。
- **界面收窄：** 管理动作进入专用面板；通用选择器只提供列表之外的管理入口。顶部加号与面板共用添加对话框，拖动和上下移共用 reorder。
- **正常路径直接返回快照：** 避免成功后固定再请求一次 list。只在冲突或未知结果时收敛状态，不引入轮询、实时订阅或后台补偿。

## 必要复杂度

| 结构 | 删除测试：去掉后会破坏什么 |
|---|---|
| 同 registry 文件的完整写事务队列 | 不同 Profile 的全文件写入可能相互覆盖；按 Profile 分锁不能解决 |
| Profile revision 与事务内 CAS | 旧窗口能覆盖新的排序或移除结果；CAS 不能移到异步准备之前单独执行 |
| dirty gate → prepare → registry commit → UI commit | 无法同时保护草稿、替代工作区可用性以及列表与 active 的引用完整性 |
| 一个待确认操作与 reconcile | 响应丢失后无法安全区分已生效与仍可能迟到的命令；单次 GET 不足以解除保护 |
| 可派生 initialized 与协调版本占位 | 无法同时保持已清空 Profile 的空态和首次未知 register 的版本隔离；不需要持久 bool 或移除历史表 |
| 清空工作区、URL 和 loading，保留 Profile | 最后一项移除后仍可能显示旧项目或停留在加载态 |

reconcile 只在未知结果使用：原业务命令先提交则版本已推进；协调先提交则旧版本命令被拒绝。重试使用原 expectedRevision，不会重复推进版本。该合同依赖同一 writer 的事务边界，不能代替多进程互斥检查。

## 风险与缺口

- **中：多进程 writer。** 进程内队列不能约束另一个 bridge；现有 standalone 入口可配置端口，host lock 的存在不能单独证明所有写入都受其保护。第一实施切片必须核对，必要时先补最小独占合同，再确定后续并发实现。
- **中：路径身份。** `normalizeRootPath()` 全平台转小写，被项目 ID 和树缓存共同消费。本方案不顺带迁移 ID；先验证支持环境的去重与碰撞处理，发现真实冲突再做身份决策。
- **待运行验证：** 文件安全替换、草稿保护、晚到回包、空态恢复与真实拖动，均是实施后的验收，不以本次文档复核替代。

## 优化空间与不采纳的扩展

首版保持逐次保存，仅一个清单操作在途、一个待确认操作记录；不增加整表草稿、“应用全部”、持久命令 ID、操作日志、撤销栈、后台重试器或实时跨窗口同步。所有新增状态均对应现有明确失败场景，没有为推测中的未来消费者预建扩展点。
