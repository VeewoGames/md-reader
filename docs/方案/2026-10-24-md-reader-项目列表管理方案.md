# 项目列表管理方案

> 日期：2026-10-24。状态：需求已确认，方案待实施授权。
> 本文是功能设计与实施切片，不代表功能已经实现，也不替代已有 Truth 与 ADR。用户已确认下面三条移除规则；本轮只编写和复核文档。

方案概述：为顶部项目选择器补齐添加、从列表移除和自由排序能力。管理对象是当前 runtime Profile 的本机项目接入清单；保留快速切换与加号，通过“管理项目…”面板集中操作。服务端 registry 继续拥有清单、顺序和当前项目，前端复用现有工作区准备、未保存保护与提交流程。实施依次完成清单事务与接口、工作区协调、管理界面与交互验收；每一阶段都以可观察的正确性结果交付。

## 一、问题、边界与不变量

### 1.1 已确认需求

用户希望对截图中的顶部项目列表进行添加、删除、自由排序，并已明确接受：

1. “删除”仅从当前 Profile 列表移除，保留磁盘目录、文档、项目配置和既有阅读状态。
2. 允许移除当前项目；处理未保存内容后安全切换到相邻项目。
3. 允许移除最后一个项目，进入仍可添加项目的空状态。

排序需要在刷新、服务重启后保持；新增项目追加末尾，普通项目切换不改变顺序。同一个项目可分别出现在不同 Profile 的列表中，移除和排序不串改其他 Profile。

### 1.2 当前事实与缺口

| 当前事实 | 对本方案的影响 | 代码或架构依据 |
|---|---|---|
| 顶部加号已有接入能力，使用路径输入并在注册后立即激活 | 复用已有入口，改善输入和错误提示，不另建添加链路 | `src/app/TopBar.tsx:735`；`src/App.tsx:1653` |
| 普通切换先检查 dirty tabs；添加入口直接注册、激活、加载 | 添加后打开也必须经过相同的未保存保护 | `src/App.tsx:1840`、`src/App.tsx:3072` |
| 服务端按 Profile 保存 `projects[]` 与 `activeProjectId`，返回数组原序 | 顺序直接保存在数组中；不新增 `sortIndex` 或浏览器排序表 | `server/project-registry.mjs:35`、`:73`、`:110` |
| 已有切换先准备工作区，再串行提交身份、树、会话和 URL | 当前项目移除应复用这套准备与提交边界 | `src/App.tsx:1490`、`:1533`、`:1581` |
| registry 目前独立读完整文件，再直接写完整文件；active 接口未检查成员资格 | 新增操作时统一所有写入口，补成员校验和并发保护 | `server/project-registry.mjs:49`、`:64`、`:102` |
| runtime registry 与项目内配置已有明确分层 | 不把接入列表或顺序写入项目仓库配置 | ADR 0022“决策”第 3—4 项 |

### 1.3 范围与不变量

- 非空列表必须有属于该列表的 `activeProjectId`；空列表的 active 必须为 `null`。首次添加选中该项目。
- 从列表移除不触发文件删除，不清理项目 `.md-reader` 或浏览器中的历史阅读状态。重新添加可恢复原有状态，前提是项目身份未改变。
- 移除非当前项目和排序只改变清单；不重载编辑器、不更换当前文档。
- 当前项目移除、添加后打开、普通切换共用未保存处理。保存失败或用户取消时，不丢弃草稿、不提交离开动作。
- 未成功持久化的顺序不能成为界面已确认状态。请求结果未知时不能假装失败回滚，也不能盲目重试。
- 保留当前 Profile 选择；最后项目移除后不退回 `default`。空态可添加、可切换 Profile，退出启动 loading 状态。

非目标：创建项目目录、物理删除目录、项目重命名、跨设备同步清单、跨 Profile 批量管理、撤销历史、后台实时推送，以及引入桌面封装或原生目录选择依赖。

## 二、新增或改变的概念、唯一 owner 与数据流

### 2.1 最少数据模型

沿用 registry 文件和 schema `version: 1`，为每个 Profile 增加非负整数 `revision`；兼容读取现有数据，不承诺旧版程序可以读写本方案的新内部形态。已初始化业务记录为：

```text
profiles[profileId]
  revision          // Profile 并发版本，旧数据缺省为 0
  activeProjectId   // 当前项目；仅空列表为 null
  projects[]        // 原有记录；数组位置就是显示顺序
```

清单变化时递增 revision，实际无变化的重复业务命令不递增；结果未知的协调操作可单独推进版本以使旧请求失效，见 3.3。旧数据缺省字段只在内存中补齐，下一次正常写入时带上；不改项目 ID，不批量重写已有目录或配置。若旧 active 引用无效，在 registry 边界按原列表首项或空列表规则修复：这是实际 mutation，必须在统一文件事务内升版本、安全落盘成功后才返回修复快照，失败明确报错，不能只发布内存修复结果。修复不扩展为历史目录或记录清理。

快照另返回 `initialized`，由该记录是否具有合法 `projects` 数组派生，不增加持久布尔字段。未使用的 Profile 可以没有 key，revision 按 0 读取；仅为未知结果协调过的 Profile 可保存 `{ revision }` 占位，仍未初始化。GET 对两者都投影 `initialized:false, projects:[], activeProjectId:null`，不补写业务字段，不触发 active 修复。所有 registry 消费者统一经过这一解释，不能直接访问占位记录的 `projects`。首次 register 成功继承占位 revision 后递增，并补齐 projects 与 active，不能重置版本。

未初始化 Profile 可沿用 ADR 0022 的首次携带当前项目行为；已初始化的空 Profile 必须保持为空。移除最后项目保留 `projects:[], activeProjectId:null`，不能删除业务字段或 key。查询与结果协调都不把从未使用的 Profile 自动初始化。实施时补充 ADR 0022，明确首次携带行为不能覆盖用户已经清空的结果；不新增移除历史或墓碑表。无效 active 修复仅适用于已初始化业务记录。

`server/project-registry.mjs` 是唯一清单 owner。`workspaceProvider` 和 bridge 只转发领域命令与类型；`App` 协调工作区切换；专用管理组件只拥有面板开关、路径输入、拖动预览和请求中状态。拖动预览不是第二份持久清单。

`src/workspace/registry.ts` 的浏览器注册表不在正式工作链路中承担新功能。当前 provider 的服务不可用分支返回空列表；不为本需求扩建第二套离线写入 owner（`src/workspace/workspace-provider.ts:47`）。

### 2.2 命令与返回合同

沿用现有 GET、register、active 接口，新增排序、移除以及仅用于未知结果的协调接口，不建立通用命令总线：

| 操作 | 建议接口及输入 | 主要约束 |
|---|---|---|
| 读取 | `GET /api/profiles/:profileId/projects` | 返回 `{ initialized, revision, activeProjectId, projects }` |
| 添加 | 现有 `POST .../projects/register`：`rootPath, expectedRevision` | 验证非空、存在、目录、可读取；重复项目保持原位置 |
| 激活 | 现有 `POST .../projects/active`：`projectId, expectedRevision` | 目标必须属于当前 Profile；不接受悬空 ID |
| 排序 | `POST .../projects/reorder`：`orderedIds, expectedRevision` | 完整、唯一、成员集合相同，只允许排列变化 |
| 移除 | `POST .../projects/unregister`：`projectId, replacementProjectId, expectedRevision` | 非当前项目无需替代项；当前项目非最后一项必须指定准备好的相邻项；最后一项替代为 `null` |
| 结果协调 | `POST .../projects/reconcile`：`expectedRevision` | 不改成员、顺序或 active；在同一写队列中使该版本的旧请求失效，再返回快照，见 3.3 |

所有 mutation 返回同一种已持久化快照；register 在保留原 `project` 返回字段的同时附带 `snapshot`，便于调用方取得项目 ID。前端无需在每次成功后再串接一次 list 请求。所有现有调用点，包括 Profile 切换时的首次自动注册和 active 写入，都同步使用此合同，不能只迁移新面板；自动注册须检查 `initialized=false`，不能继续仅判断 active 是否为空。

版本冲突返回 `409 REGISTRY_CONFLICT`，前端重读并提示“项目列表已变化，请重试本次操作”，不自动覆盖新顺序。非法排列、非法成员、不可用路径返回明确错误；不吞错后返回成功。路径检查在写入前完成，不以“至少包含一篇 Markdown”为接入条件。

数据流：管理面板／现有加号 → App 动作协调 → workspaceProvider → local bridge → registry 校验与持久化 → 返回快照 → App 在请求仍有效时投影界面。

### 2.3 持久化与并发边界

同一 `runtimeHome/projects.json` 共用一条串行写入队列，队列包住读、版本检查、成员检查、修改和安全替换；覆盖 register、active、reorder、unregister、reconcile 及旧数据修复。expectedRevision 比较必须在最终写入所在事务内执行，不能校验后退出队列、异步准备再写。队列键是规范化后的完整 registry 文件位置，不能按 Profile 分锁，因为不同 Profile 共写一个文件。

采用同目录唯一临时文件写入后替换目标文件；持久化成功后才返回快照。写入或替换失败不发布新状态，并清理本次临时文件。这里保证读者不会读到半份 JSON，不额外承诺断电后的完整持久性，也不引入数据库。

文件队列防止服务端同时读改写造成丢失更新；每个 Profile 的 revision 防止客户端持有旧快照继续修改，二者不能互相代替。

该队列只保护同一服务进程。实施第一阶段必须核对所有 registry writer 与服务启动约束，确认正式支持的运行方式中同一 runtimeHome 只有一个 writer。当前架构文档说明固定本地端口，但这不足以证明所有自定义端口／进程组合互斥；若存在受支持的多进程并写，先形成最小的独占写入约束或文件锁补充设计，再继续并发验收，不默认为已解决。

## 三、推荐决策、关键理由与一个关键失败路径

### 3.1 交互方案

保留顶部项目快速切换和加号。在项目下拉底部提供“管理项目…”入口，作为独立按钮放在 `listbox` 之外；不在 `option` 内塞入按钮，也不让通用 `TopBarSelect` 承担所有项目管理职责。

管理面板列出名称、完整路径、当前项目标记、拖动手柄、上移、下移和“移除”。上下移支持键盘；首尾按钮按位置禁用。面板内的添加入口与顶部加号打开同一个路径输入对话框，不重复实现输入、校验和错误提示，不预填具体项目的 Windows 路径。

拖动中只展示顺序预览；松手保存一次。不变的拖放不发写请求。保存期间暂停该面板后续变更，成功确认顺序，确定失败恢复已确认顺序。每次操作立即保存，不另设整表草稿、“应用全部”或“取消全部”。关闭面板不取消已提交操作。

移除前确认文案说明“仅从当前个人配置的列表移除，项目文件和阅读配置会保留”。移除非当前项目不触发工作区切换；移除当前项目时，相邻项按当前已确认顺序选择：优先下一项，否则上一项。相邻项不可用时报告原因并保留原项目，不自动遍历其他项目作为隐式回退；用户可先切换到可用项目再移除。

### 3.2 添加与工作区动作统一

添加先验证并注册，新项追加末尾，再发起现有体验中的“打开新项目”动作。项目已添加但用户取消切换、保存失败或目标工作区准备失败时，保留新增项与原工作区，明确提示“已添加，尚未切换”；不把注册和工作区加载虚构成一个跨 HTTP 事务。

重复添加不改变已有顺序，明确提示“项目已在列表中”，随后仍可通过相同保护流程打开。首次添加时服务端设置 active，前端准备失败保留注册结果并显示重试入口。

复用 `PendingWorkspaceAction`、dirty tabs 对话框、prepare 和串行 commit。扩展移除当前项目所需的动作参数即可，不新建独立保存流程、另一套 session 恢复器或通用事务框架。若为了复用而提取函数，只提取两条真实调用路径共享的准备／界面提交部分。

### 3.3 当前项目移除的正常与失败路径

1. 在确认移除后捕获操作目标、Profile、当前项目、清单版本和工作区请求代次；阻止同窗口的交叉项目变更。
2. 未保存时沿用保存全部／放弃／取消。保存失败或取消立即结束。用户明确放弃后，本次移除若随后失败，不承诺恢复已放弃内容。
3. 有替代项时只准备其工作区，不提前修改服务端 active 或前端当前项目。最后一项无需准备替代工作区。
4. registry 在同一事务内检查版本、目标和替代项，然后同时写入新列表与新 active；清空最后一项同时写入 `[]` 与 `null`。
5. 成功后同步更新项目身份、文件树、tabs、当前文档、Profile 导航投影、URL 和 pending 状态。清空时保留 Profile，清除 URL 中旧项目和文档定位，结束 loading，显示添加入口。项目持久配置和历史阅读状态仍保留。

**关键失败路径：替代项目准备成功，但 registry 提交发生冲突。** 不切换、不移除，保留当前工作区与未放弃草稿；重读清单并告知用户重试。重新操作需重新检查邻项与版本，不沿用过期候选。

**响应丢失：** HTTP 失败并不证明 registry 没有落盘，一次 GET 读到旧版本也不能证明原命令不会随后提交。前端保留现有工作区和草稿，只记录一个待确认操作（发起 Profile、动作、请求代次、目标与原 expectedRevision），暂停该窗口清单修改和依赖离开的工作区动作。

用户重试确认时调用 `reconcile(expectedRevision)`。此命令与全部业务写入进入同一文件队列，在事务内读取当前版本：

- 当前版本仍等于原 expectedRevision：只将该 Profile 的 revision 推进一次并安全落盘。仍未提交的原命令随后会因版本不符被拒绝。
- 当前版本已大于原 expectedRevision：不再改数据，直接返回当前快照；旧命令已不可能通过版本校验。
- 若同一 Profile 尚无持久记录，协调只创建 `{ revision: 1 }` 占位，不写入 projects 或 active；其读取和首次 register 合同见 2.1，不用空业务 Profile 冒充已初始化。
- 当前版本小于原 expectedRevision：属于 registry 被外部替换或回退，不当成正常成功；停止修改并明确提示版本异常。

协调成功后，无论原命令已执行，还是已被版本更新拒绝，返回快照都是可据以继续操作的状态；不宣称一定能辨认是哪一个窗口导致了相同结果。若协调响应本身丢失，可用同一个原 expectedRevision 再次协调：已推进的版本不会再次推进，仍可取得快照。

若确认当前项目已移除，保留现有按原 project/profile 归属的草稿，按返回快照准备新 active 或空态；不将旧项目草稿写入新项目。新 active 无法准备时显示恢复失败与重试入口，不继续以已移除项目身份写文档。协调失败则保持待确认，不重发旧移除／排序命令。正常请求没有额外协调往返，也不新增持久命令日志、后台重试服务或工作区副本。

### 3.4 旧回包与其他窗口

复用现有工作区 load revision 防护。管理请求还需绑定发起 Profile、请求代次与服务端 revision，避免 A → B → A 后旧 A 回包覆盖新 A。成功保存旧 Profile 的操作不因此撤销，但其回包不能把界面切回旧 Profile。

首版不增加实时订阅。其他窗口在重新读取或下一次提交发现版本冲突时收敛到新清单；收敛涉及离开本地 dirty 工作区时，仍先保护草稿。服务端发现项目已被移除时，旧窗口文档操作应明确失败，不自动重新注册该项目。

### 3.5 复用、替代与复杂度取舍

| 选项 | 决定及理由 |
|---|---|
| 单独排序表、`sortIndex`、浏览器长期顺序副本 | 不采用；已有数组足够表达顺序，增加字段会带来同步责任 |
| 先手动切换才能移除当前项目 | 不采用；不满足已确认的直接移除体验 |
| 通用 mutation 框架、事件总线、持久化任务队列、撤销历史 | 不采用；当前四类清单操作不需要新平台能力 |
| 未保存保护、候选准备、列表与 active 同次提交 | 必须保留；分别保护编辑内容、替代工作区可用性和 active 引用完整性 |
| 文件级串行与 Profile revision | 必须保留；分别防止并发写丢失和过期客户端覆盖 |
| 路径输入对话框与原生目录选择 | 首版用统一路径对话框，沿用本地服务；原生选择器留待有独立平台需求时设计 |

已有路径归一化会统一转小写，且被项目 ID 与树缓存 fingerprint 共用（`server/project-registry.mjs:15`；`server/project-tree-cache.mjs:61`）。本轮不顺带改项目身份算法；实施先验证现有 ID 在支持环境下的去重合同。若大小写敏感环境存在不同目录碰撞，拒绝将其静默合并，并先补充身份与迁移决策；不能只改归一化就宣称历史状态可继续恢复。

## 四、最小实施切片、验证与关键引用

### 4.1 第一阶段：registry 合同与桥接

目标：先建立正确的清单写入与返回合同，再开放界面操作。

- 核对同一 runtimeHome 的 writer 范围及多进程约束；有缺口时停在补充设计检查点。
- 扩展 registry 的 revision、统一串行写入、安全替换、成员校验、排序与移除；保留旧数组次序和 ID。
- 扩展 bridge、local-bridge-access 与 provider；同步迁移原有 register／active 调用点和 mock。
- 验证旧数据、重复注册原位、无变化不升版本、非法排列、移除非当前／当前／最后项、无效 active 修复落盘后重启、修复写入失败、跨 Profile 并发、过期请求、写入失败和目录保留。
- 验证未知的首次 register 经协调产生占位，重启后 initialized 仍 false；迟到旧 register 被拒绝，新版本 register 正常初始化且继承递增版本。

成果：HTTP 能返回重启可恢复的完整快照，非空 active 总属于列表；无 UI 也能证明移除不会删除目录。

### 4.2 第二阶段：工作区动作与失败恢复

目标：添加后打开、普通切换、当前项目移除共享现有保存与工作区提交合同。

- 接入移除动作参数；复用准备与提交，覆盖最后项目清空及 URL 清理；保留未初始化 Profile 首次携带，但已清空 Profile 再切入仍为空。
- 明确添加成功但未切换的部分成功结果；移除非当前项目与排序不重载工作区。
- 验证保存失败／取消、替代目录不可用、准备后 registry 冲突、提交结果未知协调、Profile A → B → A、清空 B 后切到 A 再回 B、其他窗口已移除当前项目以及刷新空态。
- 对未知结果专门验证“GET 先读到旧版本、原 POST 随后到达”“原 POST 在协调前提交”“协调响应丢失后重试”三种时序；都必须证明旧请求无法在已确认快照之后再次提交。

成果：每条失败路径都能解释 registry 与屏幕的真实状态，草稿保护不被绕过。

### 4.3 第三阶段：管理面板与真实交互

目标：在顶部保持快速切换，并提供可发现、可操作的项目管理入口。

- 增加面板、共享添加对话框、移除确认、拖动与上下移按钮、请求状态和错误提示。
- 组件验证入口语义、键盘焦点、拖动取消、重复点击、首尾限制和空态。
- 用真实鼠标验证拖动只改顺序、不误触切换；用刷新和服务重启验证持久性；再次确认磁盘项目、文档与配置均保留。
- 同步正式产品文档 `docs/04_工作区与交互.md`、`docs/06_项目与本地服务.md` 和相关限制说明，补充 ADR 0022 的首次携带与显式空态边界；只在功能实现并验证后更新已实现能力描述。

成果：添加、移除、排序和空态形成完整可用闭环。测试通过不替代真实拖动验收。

### 4.4 验证范围与实施门禁

定向扩展 `tests/server/project-registry.test.ts`、bridge 接口测试、`tests/workspace/local-bridge-access.test.ts`、provider 测试及 `tests/app` 的保存、项目切换和 Profile 回归。测试实际合同与失败结果，不为逐层转发代码机械增加镜像测试。实现后按项目要求执行相关测试与 `npm run build`。
