## 方案概述

目标是让当前 Profile 的项目清单支持添加、仅从列表移除和持久化自由排序。允许直接移除当前项目并安全切换相邻项，允许清空最后一个项目；保留磁盘目录、文档、配置和历史阅读状态。这三条规则已经确认，不再作为实施者自行选择的选项。

计划分五章：先核对 writer 与路径身份两个事实检查点，再实现 registry 合同与接口、复用工作区动作、接入管理面板，最后完成真实交互及文档验收。阶段成果依次为明确写入边界、可靠清单快照、安全工作区协调、可操作界面、完整验收证据。唯一清单 owner 是服务端 registry，前端不维护第二份持久事实。

第一章包含两个会影响具体实现路线的检查点。第二至五章只细化已稳定的需求合同与共通任务；**依赖 writer 保护方式或身份迁移的实现分支尚未展开，也未获准执行**。检查点产生额外架构／迁移需求时，先修订计划并取得对应决定，不能套用下游共通任务跳过门禁。

## 第1章：事实检查与实施路线确认

**目标／范围：** 查清同一 runtimeHome 的 writer 范围，以及路径归一化与项目身份的实际边界。只取证，不在检查过程中顺带改锁策略、ID 或缓存。**依赖：** 实施启动授权。**成果／完成条件：** 两项检查都有精确证据和唯一后续分支。**衔接：** 1.2.1 通过后，才启用第二章及相关后续任务。

### 1.1 子计划：writer 与项目身份检查

**输入：** 主方案 2.3、3.5，当前服务入口与 registry 实现。**输出：** 随本计划保存的检查结果。**非范围：** 进程治理重构、路径迁移。**风险：** host lock 不等于全部 bridge writer 受保护；改大小写规则会改变 ID 与树缓存 fingerprint。**步骤：** 依次执行 1.1.1、1.1.2。**验收：** 明确哪个事实允许保持原路线，哪个事实会触发补充设计。

#### 1.1.1 原子任务：建立 writer 边界证据

- **文件／前置：** `server/project-registry.mjs`、`server/bridge-server.mjs`、`server/service-host.mjs`、`open.mjs`、`service-scheduler.mjs`、相关 service-host 测试；先按项目要求 claw search，再精确 rg register／active／save 的消费者。
- **操作：** 追踪所有真实写入口，区分生产 host、standalone、测试调用；检查同 runtimeHome 不同端口是否可能同时写入，以及服务重启是否存在 writer 重叠。记录现有 `acquireHostLock()` 的保护对象，不将固定端口当作文件互斥证据。
- **验证与预期：** 用调用链和现有测试说明唯一 writer 是否已受强制约束。若需运行反证，仅在临时 runtimeHome、隔离端口执行，结束后关闭本次创建的实例；不操作用户实例。
- **失败处置：** 若多 writer 可达或证据不足，不选定新锁实现；在 1.2.1 补充最小独占／跨进程协调设计与验收任务，暂停依赖进程内队列正确性的实施。

#### 1.1.2 原子任务：建立路径身份兼容证据

- **文件／前置：** `server/project-registry.mjs:15` 的 `normalizeRootPath()`、`createProjectId()`，`server/project-tree-cache.mjs:61` 及 registry 测试；不得改动真实 registry。
- **操作：** 核对目录名、路径规范化、ID 与 fingerprint 的消费关系；验证同一路径不同表示可去重，大小写敏感环境的两个真实目录是否碰撞，以及移除后重新添加是否保留原 ID。
- **验证与预期：** 临时目录夹具证明现有受支持环境内的稳定身份边界；没有对应文件系统时标注未验证，不能用 Windows 夹具证明其他平台无碰撞。不默认把符号链接的全部别名统一为同一项目。
